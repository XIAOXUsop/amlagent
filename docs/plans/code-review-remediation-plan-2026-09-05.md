## 1. 目标与设计决策

本轮处理四个已发现的问题，并完成直接受影响的报告展示、角色待办、快照兼容和回归测试。

| 问题 | 目标行为 | 优先级 |
|---|---|---|
| 自动结案绕过调查契约 | 新调查契约案件必须经过人工最终处置，自动分析完成后仍可补齐调查 | P1 |
| 归并/拆分丢失模型输入 | 模型与法规检索使用本次执行冻结的完整关联预警，列表摘要只负责展示 | P1 |
| 假设改判保留旧覆盖 | 改判使相关覆盖失效，最终复核验证每条关联关系及版本 | P2 |
| 立即处理妨碍归并 | 支持先建案、归并或拆分，再显式开始调查 | P2 |

### 1.1 本版推荐采用的业务决策

**调查契约版本 1 案件统一通过人工复核形成最终结案决定。** 即便模型给出低风险、假设已排除，自动分析成功也进入 HOLD；复核员明确排除后进入 DONE，确认可疑则进入 REPORT_PENDING。版本 0 保留既有自动完成行为。

这是本计划对审查建议的具体化，属于建议采用的产品行为，并非已经存在的需求约束。它比“调查完成就允许模型自动结案”更容易保持责任、人工处置记录和可疑报告流程一致。代价是新增案件都会产生人工处置工作量，应在验收时检查角色待办容量。

本轮继续复用 PENDING、RUNNING、HOLD、REPORT_PENDING、DONE，不引入新的案件状态；用调查就绪状态和运营阶段区分“等待分析员补齐调查”与“等待复核员决定”。工作流阶段 DONE 只表示自动分析结束，不再在页面上暗示案件已经结案。

### 1.2 必须始终成立的约束

1. 版本 1 案件的自动执行不会直接写 DONE，也不会用模型输出覆盖人工调查结论。
2. 人工最终处置要求所有有效关联预警都有完整、有效且与假设一致的覆盖结论。
3. 一个执行版本内，模型、法规预检索和档案使用同一份冻结预警集合。
4. 假设版本变化后，旧覆盖不能被视为已完成，旧页面提交不能绕过版本检查。
5. 归并、拆分与 Worker 抢占交错时，数据库提交顺序决定本次执行的案件边界，不允许读取半次变更。
6. 所有终态写入继续通过现有 worker + executionVersion 条件更新；模型执行期间不持有数据库长事务。

### 2.2 统一判断逻辑

从 `blockers` 提取无副作用的判断组件，例如 `InvestigationReadinessEvaluator`。服务负责批量读取事实，判断组件负责计算结果，供详情查询、运营队列和最终复核共用。

对有效的 LINKED 预警逐条检查：

| 检查项 | 不满足时的行为 |
|---|---|
| 案件至少有一条有效预警和调查假设 | 阻止最终处置，提示缺失对象 |
| 每条预警恰有一条属于当前案件的覆盖项 | 阻止最终处置，指出对应预警 |
| 覆盖关联假设存在且属于当前案件 | 阻止跨案件或悬空关联 |
| 假设已决，覆盖不为 PENDING | 提示分析员补齐判断 |
| SUSPICIOUS 对应 CONFIRMED；EXPLAINED 对应 REJECTED | 阻止相互矛盾的结论 |
| 覆盖绑定的假设版本等于当前假设版本 | 提示覆盖依据已变化，要求重新确认 |
| 最终假设仍满足必需证据类型及证据方向要求 | 对异常或存量不完整数据阻断，不只信任状态字段 |

保留既有业务门槛：确认可疑至少需要一条有效可疑覆盖；排除要求所有假设已排除且所有预警已解释。补充尽调不是最终结论，继续允许在调查未完成时发起。

向 `CaseInvestigationView` 增加 `readyForFinalReview` 和通用调查阻断信息，同时保留两种最终决定各自的 blockers。对版本 0 返回兼容结果。

### 2.3 覆盖绑定假设版本

建议新增可空列 `hypothesis_revision`，表达覆盖决定形成时采用的假设版本；为按案件及假设查询覆盖建立合适的联合索引。

- `AlertCoverageView` 返回该字段。
- 更新覆盖的请求增加必填 `expectedHypothesisRevision`，与现有 `expectedRevision` 分别校验假设和覆盖的版本。
- 成功保存时，由服务端写入已锁定假设的当前版本；不能直接信任客户端版本作为事实。
- 新版本前端同步传入该字段。旧客户端缺字段时返回清楚的参数错误，不能默认为当前版本而掩盖陈旧判断。
- 版本冲突使用独立业务异常并映射 409。现有 `IllegalStateException` 统一映射 412，不应为此全局改动异常语义。调查尚未完成仍可使用明确的前置条件错误。

### 2.4 假设更新时使覆盖失效

在现有案件行锁保护的同一事务内：

1. 校验案件可编辑、假设版本、证据类型和方向。
2. 写入新假设状态、依据和 revision。
3. 找出当前案件中引用该假设的所有已决覆盖，将其结论置为 PENDING，清除 `hypothesisRevision` 并递增覆盖 revision。
4. 保留原分析文字作为待重新确认的参考；前端明确显示其已失效，不能把这段文字呈现为当前有效结论。
5. 使用 Audit Outbox 记录假设前后状态/版本、受影响覆盖编号和数量。自由文本遵循现有审计摘要限制。

同状态但判断依据改变也应使覆盖失效，因为引用的假设版本已经变化。完全相同的重复请求可在不修改版本的情况下返回，但不能在实际修改了依据后复用旧覆盖。

所有调查写入与最终复核继续先锁案件行。取得案件锁后再锁其下的对象，避免引入与现有路径相反的锁顺序。不得在循环中发起独立事务。

### 2.5 前端配套

`CaseDetailView.vue` 增加已决假设的“修改判断”入口，展示改判将要求重新确认哪些预警；提交后重新加载假设、覆盖和待办信息。只有角色为 ANALYST/ADMIN 且案件为 PENDING/HOLD 时显示可编辑入口。

覆盖更新遇到 409 时刷新状态，保留用户输入供人工核对，不自动重放旧判断。

### 2.6 验收

- 两个已确认假设中一个改判后，即使另一个仍然确认，可疑最终复核仍被未重新确认的覆盖阻断。
- 改判与复核同时提交时，合法结果只有“复核先提交、改判因终态拒绝”，或“改判先提交、复核因覆盖失效拒绝”。
- 改判与覆盖更新同时提交时，旧假设版本的请求不能成功。
- 审计 Outbox 登记失败，假设和全部覆盖修改共同回滚。

### 3.2 目标状态转换

| 当前条件 | 自动分析结束后 | 最终结案路径 |
|---|---|---|
| 版本 0，未触发人工处理 | DONE | 保留旧行为 |
| 版本 0，触发人工处理 | HOLD | 保留旧复核逻辑 |
| 版本 1，调查未完成 | HOLD，运营责任为分析员 | 补齐调查后进入复核 |
| 版本 1，调查完成 | HOLD，运营责任为复核员 | 明确排除 → DONE；确认可疑 → REPORT_PENDING |
| REPORT_PENDING，外部报送已受理 | DONE | 保留报告登记事务 |
| HOLD，需要补充材料 | HOLD，开放 EDD 任务 | 回传材料后继续调查/复核 |

### 3.3 后端具体修改

1. 在报告组装前计算是否受人工结案策略约束，例如 `contractManualReviewRequired = investigationContractVersion >= 1`。
2. 将它与模型契约失败、Guardrail 转人工合成为最终人工处理标志，同时传给 `FinalDecisionAssembler` 和终态选择逻辑。
3. 统一保证案件状态、`manualReviewRequired`、MANUAL_REVIEW 动作码和正文一致。不能只把状态改为 HOLD，正文却仍宣称自动完成。
4. 区分“调查契约要求人工处置”和“模型输出违规”：新增策略原因放在工作流日志或后端决策元数据中，不伪装成风险发现，不把正常报告标为 `AGENT_INVALID_HOLD`。
5. 风险级别仍由现有模型/Guardrails 逻辑决定，低风险进入 HOLD 不等于提升为高风险；不改动原始模型报告与模型质量评分。
6. 保留 `finishCase` 的 fencing 条件。自动流程只决定进入人工处理，人工调查事实的最终有效性在短事务的复核入口重新检查。

### 3.4 角色待办与 SLA

`CaseOperationsService` 当前把无 OPEN EDD 的 HOLD 统一归给 REVIEWER。修改为：

1. 有 OPEN EDD：仍归承办分析员，沿用显式截止时间。
2. 版本 1 且调查未就绪：归 INVESTIGATION/ANALYST，待办提示具体未完成项。
3. 调查就绪：归 REVIEW/REVIEWER。
4. REPORT_PENDING：仍归 REPORTING/REVIEWER。

复核员仍可查看 HOLD 案件并发起补充尽调，但最终处置按钮受同一 readiness 判断控制。

阶段起点应使用可持久化事实，不能每次查询取当前时间重置 SLA：初次补齐调查沿用案件调查起点；进入复核取自动分析完成、有效假设/覆盖最后完成、最近 EDD 回传或撤销等适用事件的最晚时间。调查改判不重置整体调查期限。为此新增稳定时钟测试，并避免队列中为每条预警单独查库。

### 3.5 页面一致性

- 自动工作流结束显示“自动分析完成，待补齐调查”或“待人工复核”。
- HOLD 详情允许分析员继续录入证据、判断假设和覆盖预警。
- DONE/REPORT_PENDING 页面只展示调查结果，不提供会被后端拒绝的编辑入口。
- 报告 SSE 终态到达后刷新案件、调查就绪状态与运营待办，避免只刷新风险报告。

### 3.6 验收

低风险版本 1 案件分析完成后仍可补齐调查；补齐不会自动结案。复核员排除后，案件、手工处置记录和档案一致。确认可疑继续完整经过待报送、登记受理、结案和退回补正流程。版本 0 的现有用例保持成立。

### 4.2 预警快照契约

新增例如 `InvestigationAlertSnapshot`，保存 alertId、externalAlertId、ruleCode、scenarioCode、hitReason、occurredAt 和 alertRevision。身份继续使用后端绑定的当前客户，不能从预警文本推导客户工具参数。

在完整尽调快照中新增：

- `alerts`：按稳定顺序保存的预警列表，建议 occurredAt 后按 alertId 排序。
- `alertsDigest`：对预警字段做规范化序列化后的 SHA-256，包含命中原因和版本。
- `snapshotSchemaVersion`：区分旧快照与包含预警事实的新快照。

原有 `sourceDigest` 保持现有业务事实口径，避免改写历史摘要的意义；新增 `alertsDigest` 专门证明预警输入一致性。不要使用有歧义的字符串简单拼接计算摘要。

### 4.3 装配和冻结时机

1. Worker 成功抢占案件后，读取属于当前案件的全部 LINKED 预警。
2. 在模型调用前冻结预警集合，并把它用于法规主题计算、Agent 上下文及加密归档。
3. `refreshCaseAlertSummary` 可以继续输出紧凑列表摘要；生产版本 1 的调查输入不再读取该摘要作为全部事实。
4. 归并/拆分继续在案件事务内完成。Worker 抢占同一案件行后，后续归并必须失败；如归并先提交，Worker 的快照必须包含该预警。
5. 版本 1 没有有效关联预警时，返回明确的工作流数据错误，禁止静默退回泛化输入。
6. 相同执行版本若已有归档，使用并校验该归档，或显式拒绝内容不一致；不能让模型使用新构建内容、归档服务却因 snapshotId 已存在而保留另一份内容。

### 4.4 法规检索与提示输入

- 对每条冻结预警的 hitReason 提取关键词，再按 scenarioCode 的确定性映射补充主题；与现有风险事实产生的强制主题合并、去重并保持稳定顺序。
- 规则编号只作为标识，不要求编号本身可被中文关键词解析。
- 模型收到逐条预警，而非截断至 255 字的案件摘要；保留编号对应关系，允许工具和报告追溯到具体预警。
- 新增文本仍按不可信业务数据处理，扩展 `PromptInjectionGuard` 的检测范围至所有命中原因；渲染时做边界隔离和敏感字段处理。加密归档可保留原始事实，模型可见副本遵守现有隐私约束。
- 对关联预警数量、模型输入长度和法规主题数量设置显式容量策略，通过样例测算确定配置默认值。超出容量必须明确拒绝或拆分为受控批次，禁止截断尾部预警后当作完整调查。

### 4.5 兼容与档案

- 旧快照缺少新增字段时仍能反序列化为旧 schema，加载、校验及档案导出继续成功。
- 版本 0 或不绑定数据库案件的独立评测夹具，由明确的兼容适配器提供旧 alertRule 上下文；不能用通用 fallback 掩盖版本 1 数据缺失。
- 更新 `InvestigationSnapshot` 的所有构造点及序列化用例，避免只修改生产入口却破坏规则/Agent 评测夹具。
- 档案增加本次执行冻结的预警版本和摘要；现有实时关联预警继续单独展示。不能把今天数据库中的预警误标成旧执行实际见到的内容。
- 保持旧档案版本可读；新档案结构增量版本化，不回写旧快照、旧模型报告或旧摘要。

### 4.6 验收

“夜间跨境转账”与“拆分现金交易”归并后，模型上下文仍逐条包含两条原因，法规主题仍包括对应主题。拆分后两边的模型上下文与各自当前关联预警一致。相同预警集合不因数据库返回顺序改变摘要；修改命中原因或版本会改变预警摘要。

## 5. 工作包 D：提供稳定的先归并后调查流程

### 5.1 API 与页面修改

`frontend/src/api/client.ts` 的三个方法增加显式选项：

```ts
type CaseStartOptions = { autoProcess: boolean }

createCase(customerId, alertRule, options)
createCaseFromAlert(alertId, expectedRevision, options)
splitAlertToNewCase(alertId, expectedRevision, reason, options)
```

要求所有内部调用点显式传值，防止遗漏调用点后悄悄恢复立即入队。

后端已支持 `autoProcess=false`，本轮保留外部接口缺省值的既有语义，降低已有调用方受影响的范围。

| 入口 | 本版推荐默认行为 | 可选行为 |
|---|---|---|
| 预警待分诊队列建案 | 创建案件，暂不启动，继续处理同客户预警 | 明确选择“创建并开始调查” |
| 普通手工建案 | 主按钮“创建案件”，保留 PENDING | 次按钮“创建并尽调” |
| 拆分新案件 | 默认暂不启动，便于继续调整边界 | 明确选择立即调查 |
| 案件详情/列表 | 归并完毕后点击“开始调查” | 无 |

### 5.2 操作反馈

- 暂不启动时提示“案件已创建，可继续归并预警”，不显示“已开始调查”。
- 保持用户在分诊工作台，刷新同客户候选案件；提供进入案件的入口。
- 开始调查前显示当前关联预警数量，并说明开始后不能归并或拆分。
- 点击后禁用重复提交，刷新案件和候选列表；服务端仍依靠 Outbox 幂等与 Worker 抢占防止重复执行。
- 与归并并发的启动，以实际事务和抢占顺序为准。若 Worker 已开始，则展示状态冲突并刷新，不自动换一个案件归并。
- PENDING 既可能是暂未启动，也可能是已经入队；界面在没有可靠任务状态时只显示“待处理/已请求启动”，不能把所有 PENDING 都宣称为未入队。

### 5.3 相关后端核对

验证 `autoProcess=false` 的普通建案、预警建案和拆分事务都不会写入执行 Outbox。开始调查仍走 `WorkflowCommandService`，不直接发 Redis 消息。对归并/拆分与 Worker 抢占增加数据库并发测试；必要时在启动命令的短事务中复查案件状态，而不是只信任控制器较早的读取。

### 5.4 验收

在 Worker 正常持续运行、无刻意延迟的环境下，用户可以创建两条同客户预警 → 第一条建案但不启动 → 第二条归并 → 查看两条关联预警 → 开始调查。整个流程不依赖抢在消费者之前点击按钮。

## 7. 数据兼容与已受影响案件

### 7.1 迁移策略

- 新增覆盖假设版本列，旧值初始为 NULL。新增字段采用增量迁移，不能重写已应用的 V25。
- 对版本 1 活跃案件，NULL 表示“没有可证明的版本绑定”，在门禁中要求重新确认；不要把当前假设版本批量回填成历史有效版本。
- 已结案历史记录和原档案保持原样；迁移不批量重新打开案件，不改写风险评级和人工决定。
- 迁移前先输出只读影响清单，统计版本 1 已 DONE 但无最终人工决定、仍有 OPEN/PENDING、或关联结论矛盾的案件。

### 7.2 已受影响数据处理

1. 对未结束案件，用新门禁暴露阻断项，由有权限的操作者补齐。
2. 对已自动 DONE 且未满足契约的案件，提供可审查的修复清单，包含案件状态、契约版本、人工处置/报告记录及阻断原因。
3. 不复用 FAILED 重试接口来修复 DONE。若确需重新打开，另行通过有案件版本/状态校验、理由及 Audit Outbox 的管理操作执行。
4. 对已经报送的案件，保留外部受理和原始调查事实，使用既有补正机制处理，不批量撤销报送。

本计划交付包括影响查询及操作说明。实际修改历史业务数据需要按具体清单执行，不属于本次“生成计划”已经完成的工作。

## 9. 发布与最终验收

- 发布前完成迁移校验、集成和端到端测试；准备活跃/已结案异常数据清单。
- 升级 Worker 前停止领取新任务并等待当前执行收敛，避免同一案件被新旧快照/结案策略交替处理。不要通过直接重置 RUNNING 状态实现升级。
- 先应用兼容的增量 schema，再以受控维护窗口切换配套后端、Worker 与前端；复查旧消费者已退出。
- 观察版本 1 自动 DONE 数应为 0、未完成调查在分析员待办可见、覆盖版本冲突提示明确、模型输入预警数量与冻结关联数一致。
- 回退时保留已写入的新列和历史事实。旧二进制能否读取新快照必须事先验证；若不兼容，应暂停消费并修正发布版本，不能直接删字段或把新 schema 当旧 schema 解析。

最终交付物：实现代码、对应回归测试、数据库迁移、存量影响查询、更新的状态流转/快照文档，以及一份标明实际执行结果和未执行项的验证报告。

完成判据：四个审查复现均不再成立；正常运行的 Worker 下可稳定完成“建案归并 → 自动分析 → 调查补齐 → 人工决定 → 报送或排除结案”；旧案件和旧快照仍可查询、导出。
