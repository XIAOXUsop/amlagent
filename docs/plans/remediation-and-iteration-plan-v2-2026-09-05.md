## 2. W1：统一调查版本冲突与草稿恢复

### 2.1 需要消除的具体行为

正常假设改判同时使假设和覆盖版本递增，旧请求先因覆盖版本不符返回 412，详情页没有刷新或保存输入。现有重新确认即便收到 409，也会丢失用户刚输入的分析。需要同时修正后端协议及两个页面入口。

### 2.2 后端实施步骤

涉及文件：

- `backend/src/main/java/com/bank/aml/investigation/InvestigationService.java`
- `backend/src/main/java/com/bank/aml/common/exception/InvestigationRevisionConflictException.java`
- `backend/src/main/java/com/bank/aml/common/GlobalExceptionHandler.java`
- `backend/src/test/java/com/bank/aml/investigation/InvestigationServiceTest.java`
- 新增或扩展调查接口/异常映射测试。

1. 盘点三个预期版本校验点：修改假设的 `expectedRevision`、覆盖自身的 `expectedRevision`、覆盖引用的 `expectedHypothesisRevision`。版本不符统一抛调查版本冲突异常，返回 HTTP 409 与稳定错误码 `INVESTIGATION_REVISION_CONFLICT`。
2. 保留案件不可编辑、证据不足、结论与状态不一致等业务前置条件的错误语义。不要通过把所有 `IllegalStateException` 全局改成 409 来处理此问题。
3. 继续先锁案件，再读取受保护的预警/覆盖/假设；不能为迁就前端而跳过覆盖版本检查，或默认接受数据库当前版本。
4. 如需让页面区分“覆盖被他人确认”和“假设被改判”，在错误响应中提供有界的冲突对象标识/类型及当前版本，或保留一个稳定错误码并统一提示“调查记录已更新”。前端不解析中文异常文案。
5. 版本冲突发生时不写覆盖、不新增成功审计事件、不进入最终处置。锁定事实后的成功提交才绑定当前假设版本。
6. 更新接口契约及正式测试；以“先真实调用改判，再提交旧覆盖”的测试覆盖两个版本同时变化的场景，不能只手工改变假设 revision 而保持覆盖 revision 不变。

### 2.3 前端实施步骤

涉及文件：`frontend/src/views/CaseDetailView.vue`、`frontend/src/utils/investigation.ts`、`frontend/src/api/client.ts` 及其测试；如抽取编辑组件，建议放到 `frontend/src/components/investigation/`。

1. 将“形成结论”和“重新确认”收敛到同一个编辑状态。保留 `caseId/alertId`、覆盖版本、假设 ID/版本、当前假设结论/依据、用户草稿与冲突状态，避免两套 catch 逻辑继续漂移。
2. 草稿在发请求前写入对话框外的响应式状态；存于当前页面内存即可。本轮不引入浏览器持久化存储调查内容。按案件与预警隔离，不能把某条预警的分析带到另一条。
3. 收到调查版本冲突后重新读取调查事实，同时保留草稿。显示最新假设状态、依据和将提交的覆盖结论；结论由当前已决假设推导。
4. 用户核对新依据并再次点击确认后才提交新版本。禁止在 catch 中静默把新版本替换进去并重放旧结论。
5. 刷新后若案件只读、预警已拆走、假设不存在或未决，停止提交并说明原因。移除当前二次提交中用 `0` 兜底对象 ID/版本，以及把未知状态默认当 EXPLAINED 的处理。
6. 刷新失败、第二次仍冲突、临时网络失败时，保留当前草稿并提供可理解的重试提示。只有成功保存或用户明确放弃编辑才清理草稿。
7. “重申判断”沿用同一冲突恢复原则。成功提示区分无变化的幂等返回与实际改判，避免幂等重申后错误声称所有覆盖已失效。
8. 配套前后端同批交付。若确需兼容旧后端返回的覆盖版本 412，应使用明确的兼容协议；不要把任意 412 都当成版本冲突自动刷新/重试。

## 5. W4：容量和失败恢复的一致性迭代

### 5.1 当前边界

上轮无法拆分的失败死路已经解除。仍可改善：`trigger()` 有容量预检，`retry()` 直接进入 `WorkflowCommandService.retryManual()`；详情页对全部 FAILED 显示拆分，后端才判断是否存在不可拆分的调查事实。若历史案件有 10 条，拆出一条后仍有 9 条，立即重试仍会再次容量失败。

### 5.2 实施方案

1. 抽取共享的执行前校验策略，归并、启动与人工重试使用同一容量来源。v1 同时检查至少一条有效关联预警；v0 保留明确的兼容策略。
2. 人工重试在案件事务中锁定并检查 FAILED 状态及容量，再完成 FAILED→PENDING 和 Outbox 入队。检查失败时保持 FAILED 与原失败信息，允许继续拆分，不先清理再补救。
3. 为页面提供服务端计算的操作能力与阻断原因，例如是否能拆分/重试、当前关联数、上限和阻断项。权限、状态、版本和调查产出由后端最终强制执行；页面提示只用于减少必然失败的操作。
4. 拆分成功后刷新源案件能力和剩余数量。若仍超限，提示还需拆出多少条；目标案件保持未启动。原案件可重试后再显示明确启动动作。
5. 对有报告、原始输出、证据、已决假设或已决覆盖的 FAILED 案件显示受限原因，不将它们等同于容量前置失败。
6. 既有 Worker 的容量防线继续保留。配置上限变更必须同时作用于预检和 Worker；不能在页面另写固定上限。

涉及：`CaseIntakeService`、`DueDiligenceService`、`WorkflowCommandService`、案件操作 DTO/查询服务、`CaseDetailView.vue` 及相关测试。

验收：10→9 时仍拒绝重试且不写新 Outbox；9→8 后正常入队；并发拆分/重试结果一致；服务端拒绝有调查事实的拆分；使用非默认容量时前后端一致。此包预计与 V2-13/V2-17/V2-22 共用集成夹具。

## 6. W5：受影响历史案件的治理

### 6.1 先形成清单，再决定开发范围

W2 输出清单按可编辑未完成、自动 DONE 无人工决定、正常人工终态、已报送四类分组。可编辑 NULL 绑定案件通过现有重新确认处理；已报送案件使用现有退回补正流程。只有确有自动 DONE 异常案件需要恢复时，才实施专用管理入口。

### 6.2 专用恢复操作设计

1. 服务端只接受 ADMIN，通过明确的案件状态、调查契约版本、预期案件修订号和理由校验。普通 FAILED 重试接口不得兼任重新打开终态案件。
2. 仅处理满足条件的 v1 自动 DONE 且无人工最终决定案件；存在有效人工决定或已报送事实时拒绝，并提供相应治理路径。
3. 恢复到 HOLD 的前提是保留现有有效报告/快照、只补齐调查与人工决定；若历史产物不足以使用，应单独设计再分析流程，不能随意重置为 PENDING。具体允许状态迁移在实施前写成状态表。
4. 单个事务完成状态转换、版本递增和 Audit Outbox 记录，记录操作者、原因、前后状态及关联历史产物。保留历史归档，不改写已有报告或伪造 reviewedAt。
5. 操作需要用户核对具体案件的恢复预览后明确提交；禁止以一条批量 UPDATE 完成所有恢复。支持重复提交幂等，提供可追踪的操作结果。
6. 测试正常恢复、旧版本、重复请求、非管理员、已人工结案、已报送、审计失败回滚等分支。

交付依赖：影响清单与业务恢复范围已经确定。若清单为空，本轮记录无需启用此能力即可；不能为了形式完整对历史案件进行无必要修改。

## 7. W6：持续可观测性、兼容性与质量迭代

按以下顺序形成可独立验收的小批次，不并入首批缺陷修复的大改动：

1. **调查契约监控。** 增加 v1 自动 DONE 异常计数、覆盖版本冲突率、按原因统计的就绪阻断、容量拒绝和失败恢复结果。指标只使用有界标签，案件 ID/原始调查文字放在受控日志或审计记录中。
2. **前端最终状态一致性。** 针对 SSE 重连、丢失终态事件和用户长时间停留，建立重连后查询对账；用断开连接后完成案件的测试证明状态最终与 API 一致。当前未完成这类 E2E，不先宣称已有缺陷或已经可靠。
3. **双向快照兼容。** 新程序读取旧快照、旧发布产物读取新快照分别测试；不能以新代码读取缺字段 JSON 推断旧二进制一定能处理新字段。核对同执行版本幂等归档的摘要覆盖范围，若有缺口再决定新增 payload digest，保留历史摘要语义。
4. **真实模型/检索质量基线。** 使用冻结且经领域复核的合成或脱敏评测集，分单预警/多预警、可疑/解释、注入/敏感内容测试。分别报告调查事实覆盖、法规依据正确性、严重错误率和成本/延迟；真实模型评测与确定性门禁分开。
5. **再决定模型分级或检索优化。** 只有质量/成本数据表明收益后才推进 CostRouter 或检索实现调整，每次有固定对照集及回退开关；不在流程修复验收期间同时改变评分口径。

## 9. 发布、回退和最终签收

### 发布前

- R1/R2 已有修复代码及正式回归，现有默认测试/构建未回退。
- V2-01—23 的适用项全部有执行结果；未执行项不可写通过。缺陷修复与验收材料引用同一个待发布版本。
- 先在对应 schema 执行迁移前清单，再应用 V26、执行迁移后清单；如果环境已在 V26，不回退数据库去跑 V25 阶段脚本。
- 记录可编辑存量、异常终态和已报送的处置方式；数据清单使用部署实际容量。
- 更正实施说明中的测试总数、冲突输入保留、SQL 静态核对与实跑的区分。

### 发布操作

1. 暂停领取新工作流任务，等待现有执行收敛；不要直接把 RUNNING 改为 PENDING。
2. 按环境当前版本应用所需增量 schema，再切换匹配的后端、Worker、前端；确认旧消费者已退出。
3. 对合成验证案件执行一次“建案归并→分析 HOLD→补齐调查→人工最终决定”，同时抽查一条存量覆盖重新确认。
4. 检查 v1 自动 DONE 异常、冲突、容量拒绝、待办就绪分流与 Outbox 状态；出现契约破坏时先暂停相关操作/消费并调查。

### 回退要求

保留已写入 schema 和历史事实，不删除版本列或快照摘要。不把“新代码读取旧 schema”当成旧二进制读取新数据的证据；旧发布产物必须先通过兼容测试。若未证明兼容，采用暂停消费并修复当前版本的方式，不能强行回退消费者。

### 最终交付清单

实现代码、正式回归用例、分阶段 SQL、迁移和隔离环境配置、测试/并发/E2E 结果、更新的实施说明、发布及回退记录。每个条目写明完成、失败或未执行及原因。

最近一次修复版本可签收的标准：两类确认缺陷消失；正常 Worker 下能稳定完成建案归并、自动分析、调查补齐、人工决定和报送/排除闭环；存量 NULL 绑定可直接重新确认；真实事务与迁移验收通过。W4—W6 按各自范围独立签收。
