# 下一代迭代计划书：集团代付后的退货退款复核

日期：2026-09-08。代码基线：`7ad1ff5`。状态：**方案，尚未实施**。v4 是本计划迭代编号，不表示已将系统 `investigationContractVersion` 改为 4。

依据：[本轮全量回归报告](/D:/JCode/docs/reviews/full-regression-and-business-review-2026-09-08.md)、[原代付专项 v3 计划](/D:/JCode/docs/plans/third-party-goods-payment-verification-plan-v3-2026-09-08.md) 和当前实现。旧闭环计划中已完成的迁移、摘要约束、token 修复和数据库幂等不重复列为新功能；未完成的事实采用、范围冻结和义务绑定作为前置条件。

## 1. 本轮只深挖一个业务问题

**一笔集团代付已被解释并复核后，发生部分退货退款，系统如何证明这笔退款仍有商业依据，或者准确说明原解释在哪一部分不再足够？**

当前 Q6 已经提示调查者关注退款、冲正、授权撤销，但主要依靠草稿文字表达。系统尚不能稳定回答：退款对应原来哪笔资金、哪部分货物义务，实际收款人是否有权收取，原先的授权是否涵盖退款，原案件决定是否需要补充调查，以及哪个具体事项仍由谁跟进。

这是对现有集团代付能力的纵向深化。交付成果是一条能从真实业务事件走到人工处置和可回放档案的路径；不以新增多少字段、接口或问答模板作为完成标准。

### 1.1 明确业务边界

首批支持：境内人民币、自营商品贸易、合同买方 B、集团实际付款人 P、合同卖方/被调查客户 A；已交付结算的集团代付，在之后发生全部或部分退货退款。允许一笔原付款对应多次退款，以及一笔退款对应多笔原付款，但必须逐项分配。

首批不自动处理跨境换汇、债权转让、多层轧差、平台分账或个人代付。遇到这些情况保留原预警和调查记录，进入人工范围评估，不自动套用当前配方。

现有 `GOODS_GROUP_PAYMENT_V1` 支持已交付结算；不能把它直接用于集团预付。部分交付和集团预付款作为后续独立政策扩展，本轮先做好“已交付后部分退货”。

本系统负责调查、证据和人工复核，不直接执行资金退款、冻结账户或自动报送。下文“阻断”均指阻止采用不充分的解释/最终排除。

## 3. 贯穿实现与验收的固定案例

### 3.1 初始状态

买方 B 向卖方 A 采购 44 万元商品并完成交付。集团付款主体 P 依据授权 AU-01 支付两笔：T-1001 为 32 万元，T-1002 为 12 万元。合同、交付、集团关系、授权主体、有效期间和两笔执行情况均已有可采用的核验。复核员在依据 B1 上作出本次预警排除决定 R1。

随后 B 退回其中价值 12 万元的商品，A 发起退款。系统必须保留当时 R1 的依据，同时调查这次变化。

### 3.2 三种结果，不能用同一个“已解释”覆盖

| 分支 | 新事实 | 应有结果 |
|---|---|---|
| 正常原路退款 | A 将 12 万退给 P，退货、原付款分配和收款账户已核对 | 新事件的退款解释可提交复核；当前保留货款 32 万，已核实退款 12 万；R1 原文不改写 |
| 退给合同买方 | A 将 12 万退给 B，但原付款来自 P | 先核实 B 收款权限及 P/B/A 之间的结算安排；同集团或合同买方身份本身不足以证明退款收款权，补齐后可人工确认合理 |
| 退给无关账户 | A 将 12 万退给 D，只有口头“集团安排” | 形成退款收款权限/资金用途未解决事项；禁止自动沿用原排除结论；是否形成怀疑由复核员结合证据决定 |

必须同时保留“原授权在付款时是否有效”和“后来是否被撤销/否认”。后来的撤销不自动证明此前付款未经授权；后来的确认文件也不自动证明付款当时已经获得授权。

### 3.3 两个维度分别表达

1. **历史决定是否需要纠正**：取决于新证据是否否定当时事实或揭示当时存在的遗漏。
2. **本次新增退款是否解释充分**：取决于本次退款的主体、权限、金额和商业原因。

不把每一笔正常退款都判为历史错误，也不因为历史决定未变就忽略新退款。新调查通过后形成 R2，并关联 R1 和新事件，不覆盖 R1。

## 4. 第一阶段：先修复本轮发现的错误放行

### 4.1 当前有效核验规则（FR-01）

新增统一可采用性评估器 `EvidenceAdmissibilityService`，由单元提交、readiness、复核预检和最终提交共同调用，返回结构化 `blockerCode + claimId/questionCode + artifactVersionId + verificationEventId + remediation`。

同一材料可以有多种核验动作，不能粗暴取整个材料的最后一条事件代表所有事实。按“材料版本 + 核验对象/事实键 + 核验用途”形成核验链，使用明确的更正/替代关系或稳定事件序号处理最新有效状态。

最小规则：

- `CONFIRMED` 仅在对应事实范围内提供支持；`UNRESOLVED` 不再提供该范围的肯定支持。
- 完整性不符、被撤回的采用事件、未取得内容、错主体/错案件的材料均不能凑数。
- 对具体事实的新否认/更正使依赖该事实的采用关系失效，不能通过更换幂等键恢复。
- 每题/每 Claim 单独评估，不共享前面题目的累积材料集合；反证引用与支持引用分别处理。
- 新核验完成后允许恢复调查并生成新提交；保留失效旧版本和恢复理由。

验收：FR-01 原反例必须被拒绝，补入有效确认后正常通过；Q1 核验不能替代 Q2；同一材料不同事实的核验互不错误覆盖。

### 4.2 不适用规则（FR-02）

在政策版本中维护允许例外的问题、前提和所需替代事实。用户只能请求例外，服务端输出核定结果。普通已交付货款的全部六题不适用必须拒绝；对政策明确允许的非核心问题保留正常成功路径。

策略调整与版本号一起保存到提交；不能因当前政策被修改而改变历史提交解释。对存量无证据“不适用”提交标记待再核验，不补造证据或静默转成已通过。

### 4.3 义务必须绑定业务对象（FR-03）

将“提交有 followupRequired + 案件有任务”替换为明确的义务清单。每项包含需要核验的事实、关联金额/交易、截止节点和完成条件；任务逐项承接。

同一任务可在未来支持多项义务，但必须显式列出全部 obligationId，逐项完成、逐项验收；第一版可限制为一任务一义务以降低复杂度。不得因为任务数等于义务数就视为覆盖。

### 4.4 评测必须证明实际可用（FR-04）

CI 启动前核对本地模型制品和摘要、独立索引命名；建立 active 索引后验证可回答样本能返回依据。A/B 必须记录实际执行管线和重排调用，不允许全拒答冒充四路比较。

质量门禁按现有评测集和配置设置，至少包含有效可回答样本、Recall/nDCG、拒答、冷 P95；环境资源不足应报告环境/性能失败。先固定样本、机器条件、模型与索引版本，再讨论阈值调整。

## 5. 第二阶段：打牢退款复核依赖的事实模型

### 5.1 冻结服务器预警范围

实现 `AlertScopePort` 或等效上游接口，获取预警命中的全部 transactionId、触发规则版本、来源批次及金额；区分命中交易与辅助交易。冻结为 `AlertScopeSnapshot`。

客户端的 reviewedTransactionIds 只表达调查进度，不定义预警全集。缺少某笔命中、来源无法枚举或来源版本变更，分别返回范围缺口；允许记录未知，禁止假定枚举完整。

退款是后续新事件，可以关联历史付款快照，但不能偷偷插入或删除旧 R1 的冻结范围。新范围形成新版本 B2，明确新增与移除原因。

### 5.2 原文、版本与支持关系

复用 `EvidenceArtifactVersion` 和 `ClaimEvidenceLink`，补实际写入链：来源返回的原文/受控对象地址、服务器摘要、取得时间、来源家族、定位信息，关联到具体 Claim 版本及核验事件。

材料内容保存在工作区测试存储或受控对象存储适配器；上线前提供授权读取、保留策略和备份能力。抓取失败仍记录 UNAVAILABLE/NOT_FOUND，不写伪摘要，不形成可采用正文。

同一原始文件的转发件、截图和摘要属于同源家族，不能当作多份独立确认。需要独立来源的事实按政策评估；不机械要求所有退款都收集同样数量的材料。

### 5.3 时间规则

每个授权/退款/否认事实分别保存：业务发生或生效时间 `effectiveAt`，系统得知时间 `recordedAt`，以及来源版本。未知时间显式为空并附原因，不拿上传时间代替业务时间。

授权覆盖校验使用付款发生时点；退款收款权限使用退款对应时点。撤销时间、追认时间与系统获知时间不混为一谈。时间冲突进入待调查；系统不替代人工作出授权法律效力认定。

## 6. 第三阶段：新增退款复核链

### 6.1 建议新增/扩展的数据对象

以下是逻辑模型，实施时优先复用现有实体；迁移编号在开工时检查 HEAD 后分配，不修改已应用 V27～V31。

| 对象 | 核心字段 | 约束 |
|---|---|---|
| PaymentAuthorityVersion | authorityRef、授权人/付款人/收款人稳定主体 ID、有效期间、订单范围、金额上限、撤销/更正关系、材料版本 | 集团关系与授权关系分开；版本只追加；未知字段不能伪造默认值 |
| PaymentAllocation | 原 transactionId、orderLine/obligationId、amount、currency、authorityVersionId、basisId | 总分配不得超来源金额；跨单元重复占用须拒绝；金额使用定点十进制 |
| RefundEvent | sourceSystem、externalEventId、原交易线索、实际付款/收款主体和账户标识、amount、currency、发生/取得时间、eventStatus | 来源幂等键唯一；客户声明与银行已入账事件分开；同 ID 不同内容产生更正冲突 |
| RefundAllocation | refundEventId、originalPaymentAllocationId、returnedObligationId、allocatedAmount、version | 退款与原付款显式多对多；每笔退款总分配不得超过退款额；原额度不能重复退 |
| RefundClaim | 退款原因、原付款对应、收款权限、退货/金额依据、执行一致性等事实状态 | 每个结论关联核验动作及支持/反对证据；未知和冲突单独记录 |
| ReviewObligation | obligationId、claimId、allocationId、金额范围、originSubmissionId、originReviewId、dueAt、完成条件类型与参数 | OPEN/ASSIGNED/SATISFIED/CANCELLED 有明确迁移条件；完成须有核验凭据 |
| DecisionImpactAssessment | 新事件、被影响 basis/submission/review、影响类型、原因、评估人、版本 | 保留历史；影响范围可追溯；技术失效与人工怀疑结论分开 |

退款收款人权限不得只用“和原付款人名称相似”判断；使用主体及账户归属核验。名称变化和别名属于身份消歧，不直接等于第三方退款。

### 6.2 金额账的口径

以已核实、已入账且未冲正的原支付分配为起点；同币种内计算：

```text
原分配付款额
  = 已核实退款额 + 当前仍保留的付款额

当前仍保留的付款额
  = 已解释的保留货款额 + 尚未解释的保留差额

一笔退款事件的分配合计 <= 该退款事件金额
同一原付款分配的累计有效退款额 <= 原付款分配金额
```

“申请退款”“约定退款”不提前减少实际资金余额；另列待执行退款义务。冲正通过反向事件撤销其资金效果，保留原记录。退款的手续费、折价、赔偿等差额单列已核实调整项，禁止把误差全部塞进一个默认容差。

示例：44 万原付款、12 万实际已退，则当前保留 32 万。若只退 8 万、另 4 万承诺下周退，显示已退 8 万、保留 36 万，其中待退义务 4 万；不能把实际已退显示为 12 万。

金额一致只证明算术闭合，不能单独证明商业理由成立。退货数量/计价、收款权限和执行主体仍需分别核验。第一版仅 CNY、分为最小单位；禁止浮点数和跨币种直接相加。

### 6.3 状态与决策表

退款事件事实状态与调查处置分开。事实可为 REQUESTED、POSTED、REVERSED；调查可为待关联、待核验、存在冲突、可提交、已复核。状态名称在 API 定稿时统一，避免复用 CaseStatus 表达所有含义。

| 条件 | 系统建议/门禁 | 人工操作 |
|---|---|---|
| 退款已入账，原付款、退货原因、金额和权限均有当前有效支持 | 可提交退款解释 | 独立复核后形成 R2，记录旧决定影响范围 |
| 退给原付款主体但无退货/解除依据 | 原路不自动免责，退款原因未解决 | 补核验商业原因及金额依据 |
| 退给买方 B，已核实有收款权限且结算义务清楚 | 可进入人工解释复核 | 记录权限来源、P 的结算关系及范围 |
| 退给 B/D，权限未知或被否认 | 阻断退款解释成立与依赖该解释的排除 | 形成具体问题与义务；怀疑结论仍需人工理由 |
| 原付款或退款只关联了子集 | 返回未分配交易/金额 | 补齐关联或记录范围未知 |
| 退款请求尚未入账且未到期 | 不算已退款；建立执行核验义务 | 只在政策允许的当次处置中带责任接续 |
| 退款已到期未执行 | 新增逾期关键事项 | 通知责任人，重新调查，不自动确认可疑 |
| 新材料否定原授权在付款时已存在 | 原授权事实受影响，相关采用关系失效 | 对 R1 形成纠正/补充调查流程，历史原文保留 |
| 付款后才撤销授权，无追溯否认 | 原付款时有效性和后续权限分别显示 | 评估新退款是否需要新的权限依据 |
| 有明确怀疑但仍有未解决义务 | 按现有确认可疑政策评估，不强制先把全部未知解释掉 | 符合政策的义务原子接续，明确未解决事实及负责人 |

“没有证据解释”不等于“已有证据证实可疑”；界面、日志、报告和指标均保留这一区别。

### 6.4 新事件如何影响旧决定

采用 `RefundEvent → 关联原分配 → 确定依赖事实 → ImpactAssessment → 新调查/复核` 的确定性流程。模型可以提取候选关系或生成摘要，但不直接写入已核实关联和最终决定。

影响类型至少包括：只需记录的正常后续事件、需要补充核验、否定旧支持事实、来源更正/撤回。未完成匹配时禁止标记“无影响”。

重复事件只处理一次；同一旧决定同时收到两次退款，事务锁/乐观版本保护累计额度与事件去重。已终结案件出现重要新事实时建立关联再调查记录或新案件，并保存 oldCaseId/oldReviewId；具体采用重开还是关联新案需与当前 CaseStatus 状态机一致，不能绕过状态迁移直接改已完成案件。

## 7. API 与页面的具体交付

### 7.1 API 草案

以下为待实施接口，先与现有控制器风格对齐再定稿，不表示已存在。

| 接口 | 主要输入/输出 | 权限及一致性 |
|---|---|---|
| `POST /api/cases/{id}/refund-events` | 来源事件引用/手工声明类型、金额、主体、时间、evidenceVersionIds；返回 eventId、版本、待关联原因 | 分析员/授权导入；手工录入不能自标银行已核实 |
| `PUT /api/cases/{id}/refund-events/{eventId}/allocations` | 原分配 ID、金额；返回剩余未关联金额和冲突项 | expectedRevision；服务器查来源金额，不信任客户端余额 |
| `POST /api/cases/{id}/refund-events/{eventId}/verification-actions` | 事实键、具体方法、观察、结果、限制、材料版本 | 核验角色；校验来源/事实对应关系；追加事件 |
| `GET /api/cases/{id}/refund-events/{eventId}/impact` | 影响的旧决定/提交、原因、金额范围、待办 | 只读；显示计算版本和不确定项 |
| 扩展现有 `POST /api/reviews/{caseId}/prechecks` | decision、basisToken、expectedReviewRevision、continuationTasks | 使用拟接续后的虚拟状态计算，不写库；返回精确未覆盖义务 |
| 扩展现有复核提交 | 同一计划、依据 token、版本、请求幂等键 | 案件/义务/分配在事务内再校验；同时落复核、接续、采用关系与审计 outbox |
| 历史档案读取按 reviewId | 返回当时 basis、采用提交、原文版本、事件、义务接续 | 禁止拿当前 draftJson 替代已采用 payload |

统一错误契约示例：`REFUND_UNALLOCATED`、`REFUND_OVER_ALLOCATED`、`RECIPIENT_AUTHORITY_UNRESOLVED`、`VERIFICATION_SUPERSEDED`、`OBLIGATION_UNCOVERED`、`BASIS_CONFLICT`。错误应定位交易和事实并给可操作修复提示。

预检与提交使用同一评估函数。预检成功后数据发生变化，提交返回版本冲突并要求重新核对变化；不自动重新取 token 后重试决定。

### 7.2 分析员工作台

在案件详情增加“后续退款”区域，呈现原付款 44 万、已退金额、待退金额、未解释差额。每条退款展示原交易、订单/退货项目、实际收款主体、权限状态和核验状态。

点击未解决项直接到对应事实及材料定位，不要求用户在长篇报告里寻找。草稿允许分次保存；提交前展示这次会影响哪些历史支持事实以及尚缺哪项核验。

退款收款人不同于原付款人时展示身份和权限核对表，不默认勾选“同集团所以可退”。界面同时显示支持材料和相反材料，不能只显示最新正向摘要。

### 7.3 复核员界面

从“变化摘要”进入，按旧 R1、新事件、当前 B2 并列核对。提供明确的接续计划编辑器：每项 obligation、原始业务范围、承办人、截止时间、完成标准类型、所需核验动作。

先允许编辑计划，再调用拟议状态预检；不要在用户录入计划前因当前有 OPEN 任务就退出。提交按钮只展示预检结果，最终仍由服务端在事务内重评。

自审限制和后台权限保持有效；ADMIN 的管理权限不应默认绕过业务独立复核规则。页面角色菜单测试之外，需要实际执行 API 权限和自审拒绝场景。

### 7.4 完成任务与档案

承办人提交具体核验动作及结论，系统核对对应事实、金额和证据，复核后才完成 obligation。填写“已联系”或上传任意文件不能自动关闭退款权限问题。

档案必须能回答：R1 当时采用了什么；何时得知退款；R2 为什么维持、补充或纠正原判断；12 万分别去了哪里；还剩哪项义务、由谁负责。历史导出按 reviewId 固定，当前草稿另列为未采用内容。

## 8. 数据迁移、并发与回退

存量提交区分已有完整链、仅草稿文字、无法重建。对后两类标为 `LEGACY_UNVERIFIED` 或等效迁移状态，保留原决定，不自动补成已核实退款或有效授权。

先增量建表/字段并双读验证，再开写入；旧页面在新开关关闭时仍可读历史。新增事件、分配和义务采用关系只追加版本；修正通过新版本生效，审计保留旧值。

外部抓取在事务外取得明确版本并计算摘要；入库及采用在短事务内绑定该版本。对同一原分配并发退款，使用稳定锁顺序或版本条件更新保护剩余额度。

复核事务内顺序建议：锁定案件/关联分配及义务 → 校验版本和依据 → 验证拟议接续 → 创建复核记录及 originReviewId → 创建/承接任务 → 写采用关系、状态及 outbox → 一起提交。任意中间步骤失败不得留下半承接任务或已变更的最终状态。

按客户端请求幂等键和上游事件幂等键分别去重。同键同请求返回原结果；同键不同有效载荷返回冲突。消息重复、乱序或重启后重投不能重复占用额度。

回退以功能开关停止新退款自动关联和新政策采用，保留事件和人工调查入口；已形成的新事件/复核不删除，不回写旧 schema 伪装未发生。灰度前演练恢复旧界面、重放未消费事件和继续履行已接续义务。

## 11. 业务指标与灰度验收

先采基线，再设置改善目标，不凭本轮代码审查宣称已经降低误报率。样本建议从至少 30 个经业务负责人确认的合成或脱敏案例起步，覆盖上述正常与异常分支；样本构成、标签版本和争议处理须记录。它是试点起点，不足以证明生产统计效果。

| 指标 | 精确定义 | 初始验收要求 |
|---|---|---|
| 错误排除数 | 在禁止 EXPLAINED/最终排除的签认场景中实际放行次数 | 验收集为 0；一例即阻止灰度扩大 |
| 正常案例可办结率 | 依据完整正常场景中，合格角色可完成复核的比例 | 验收集 RF-06/08 等为 100%，防一律拒绝 |
| 金额覆盖率 | 已关联退款金额 / 应关联有效退款金额，按币种单独计算 | 未覆盖金额必须显式可见；拟排除场景无隐匿差额 |
| 义务承接率 | 有有效、精确绑定承办责任的未完成义务 / 应接续义务 | 允许带后续义务的最终处置中为 100% |
| 再调查响应时间 | 从事件进入系统到影响评估及责任待办落地的时间 | 先记录分位值和队列延迟；试点目标由业务 SLA 确认 |
| 调查操作成本 | 每案人工活跃耗时、重复索取同源材料次数、退回补件轮数 | 与同复杂度旧流程比较，不设未经测量的提升百分比 |
| 档案可回放率 | 抽样决定能恢复当时正文、核验、范围及义务版本的比例 | 验收集 100%；缺原文不得记为成功 |
| 检索可用性 | 可回答集 Recall/nDCG、不可回答集拒答、真实重排占比、冷 P95 | 分项达到批准基线；全拒答不能视为高质量 |

灰度顺序：开发隔离库 → 业务签认样本 → 只生成建议的影子运行 → 小范围人工采用。每一步需要上一步的反例、成功对照、数据一致性与回退证据。自动错误排除、金额重复分配、义务丢失、历史原文无法回放任一出现，停止扩大并保留证据。

## 12. 开工前要形成的具体评审材料

G0 可直接实施。G1/G2 开工前由产品和业务负责人整理下列材料并在实现过程中确认，不需要停在泛泛的“需求再讨论”：

1. 固定案例及三条退款分支的事实表，明确什么材料支持收款权限，什么只是集团关系。
2. 原付款与退款各自的上游字段样例，确认稳定 transactionId、事件唯一键和更正机制；取不到的字段标明未知路径。
3. 退款差额类型表：退货折价、手续费、赔偿、冲正等分别由什么证据支持，禁止统一容差。
4. “历史决定需纠正”与“只调查后续退款”的业务边界，及对应案件重开/关联新案的审批责任。
5. 义务完成标准和责任分工：核验原付款对应、退款商业原因、收款权限、到账事实各由谁完成/谁复核。
6. RF-01～30 的输入、预期 blocker、预期金额账、最终状态和档案内容；争议样本进入待确认集，不强行当金标。

最终交付包应包括代码与迁移、接口契约、签认场景、全量测试日志、真实数据库行级证据、三角色浏览器记录、R1/R2 档案对照和回退演练记录。只有这些证据一致，才能将“关注退款的提示”验收为“能持续复核退款的业务能力”。
