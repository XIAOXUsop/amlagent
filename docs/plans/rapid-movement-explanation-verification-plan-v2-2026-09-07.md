# 企业货款快进快出：合理解释核验专项计划 v2

更新日期：2026-09-07。状态：**设计稿，供实施；新增能力尚未实现。**
本版替代 [v1 计划](rapid-movement-explanation-verification-plan-2026-09-07.md)中的实施设计；原六笔交易示例与来源研究继续保留为背景。代码审查依据：[业务审查报告](../reviews/business-review-and-focus-2026-09-07.md)。

## 1. 本轮优化后的结论

**将“填六个问题”推进为“逐预警提出业务解释，用具体核验动作处理差异，再形成可复现的人工决定”。** 主线仍是境内企业货款快进快出，不扩展股权图谱、跨银行资金网络或通用流程平台。

v1 已有正确方向，但以下设计不宜原样实施：

| v1 的不足 | v2 的明确决定 | 对交付的影响 |
|---|---|---|
| 一个假设决定所有关联预警的方向 | 核验和结论先落到逐预警单元，假设作为汇总；允许同案合理解释与可疑预警并存 | 必须同步修改 v2 后端门禁、前端冲突判断与档案语义 |
| 把已交付货款与预付款放入同一材料要求 | 首批实现已交付结算、合同预付款两种配方；先判断适用性 | 合法预付款不因“没有尚未发生的交付”被机械阻断 |
| 六问题“满足”缺少可操作的含义 | 每项包含可观察事实、材料定位、核验方法、局限和人的判断 | 不把核验按钮或附件数当成证据充分性 |
| 新证据、编辑、版本计数混在一起 | 区分草稿版本、不可变提交、案件事实序号；用一个服务端依据令牌控制最终提交 | 防止版本相互等待、旧 API 绕过和连续无关冲突 |
| 可疑路径复用旧 EDD 门禁，可能无限等待 | 明确补件停止/升级条件及持续跟进任务，保留未解决事项 | 需要修改 EDD 校验、队列和报送后的补件权限 |
| 只测错误放行，容易奖励“全部阻断” | 同时测合法解释误阻断、未知被强行定性、反证遗漏和引用真实性 | 使用成对案例、冻结集合和明确分母 |

**推荐范围：先交付完整人工闭环与两种配方，再加 AI 辅助。** 人工业务闭环估计 30–41 人日；AI 与对照实验另估 3–5 人日。较 v1 增加的工作集中在混合结论和 EDD 接续，这是修正现有流程冲突所需的成本，不用隐藏依赖维持原估算。

## 2. 依据、假设与本次边界

现行报告规定要求记录人工分析及合理排除理由，并将可疑判断与客户尽调相互验证；本次重新核对的文本是人民银行 2025 年第 10 号令，而非征求意见稿。[官方文本，第 4–5 页](https://www.pbc.gov.cn/zhengwugongkai/4081330/4406346/4406348/5885116/2025111915332696325.pdf)

客户尽调措施应与风险情形匹配；强化尽调可涉及业务目的、资金来源用途及必要的材料核实。该要求支持针对问题开展核验，不意味着所有货款都必须采用固定附件清单。[人民银行 2025 年第 11 号令，第二十七、二十八条](https://www.pbc.gov.cn/zhengwugongkai/attachDir/2025/12/2025122909264498909.pdf)

以下配方、问题等级、时间参数、令牌及表名均为项目设计，不是监管指定实现。其业务适用性需通过本项目案例评审；演示不宣称已获机构或专家认可。

首批范围固定为：境内普通贸易企业、CNY、一客户一案件、已命中的 RAPID_MOVEMENT 预警、受控合成材料及现有冻结数据。支持同案多预警；不改变同客户归并边界和 Worker 容量限制。

本轮只做方案修订、代码接口核对和设计规则检查；不重跑生产功能验收、不修改业务源码。上轮数据库迁移/并发/E2E 未完成的结论仍有效。

## 3. 正确的业务粒度：案件、假设、预警核验单元

### 3.1 三层职责

| 层级 | 表达什么 | 不能表达成什么 |
|---|---|---|
| 案件 | 本客户本轮全部有效预警的调查及最终人工处置 | 一份材料合理就全案低风险 |
| 假设 | 同一场景下是否仍有支持风险怀疑的已评估发现 | 强迫所有预警拥有同一结论 |
| 预警核验单元 `AlertExplanationUnit` | 一条预警的范围、解释、六问题、反证及分析员建议 | 把解释未成立直接映射为客户可疑 |

首批一个单元对应一条有效预警，属于案件内一个假设。若该预警涉及多批货款，单元内分别列订单/交易关联，每条关键问题按批次记录适用情况；只有整个预警范围均满足解释要求，单元才可建议 EXPLAINED。暂不另建可跨客户复用的业务批次管理系统。

### 3.2 范围完整性

- 服务端冻结 `requiredAlertIds` 和每条预警的 `triggerTransactionIds`；缺少监测输入映射时记录 `ALERT_SCOPE_UNRESOLVED`，不得把人工挑选的六笔当成已证明的完整命中集合。
- `reviewedTransactionIds` 至少覆盖可定位的命中集合；额外上下文交易单独标注，包含选取理由和观察期间。
- 分析员可将明显无关的上下文交易移出，但不得删除命中交易来使解释更容易通过。源预警更正必须生成有来源的新范围版本。
- 同一交易可关联两条预警，案件金额按唯一源身份/版本去重；两条预警仍分别说明为什么被解释或支持怀疑。
- “范围已枚举”与“范围内事项均已解释”分别记录。前者可以包含已披露未知；后者不能包含关键未知。

### 3.3 混合结论的例子

同案 A-01 是有已核验采购依据的 60 万元货款，A-02 是收款主体和客户说法矛盾的 40 万元转账。允许 A-01=EXPLAINED、A-02=SUSPICIOUS，假设汇总为 CONFIRMED，案件供人工确认可疑。不得为了符合旧假设映射，将 A-01 改写为 SUSPICIOUS。

假设汇总规则：任一已提交、当前有效单元有人工支持的 SUSPICIOUS，汇总 CONFIRMED；全部 EXPLAINED 才汇总 REJECTED；其他情况 OPEN。汇总 CONFIRMED 不等于案件已经最终完成，仍须检查全部范围、已披露未知和最终权限。

## 4. 两种业务配方与适用性

先核对经营角色、付款阶段、付款主体，再选配方。选择配方是有依据的人工判断，不能由模型根据“买卖合同”四个字直接确定。

| 配方 | 适用前提 | 主要核验链 | 不应机械要求 |
|---|---|---|---|
| `GOODS_SETTLED_V1` 已交付货款结算 | 客户解释为已交付货物的销售收款和采购付款 | 买卖双方/授权 → 订单 → 实际交付或可接受替代核验 → 收付记录 → 差额/账期解释 | 固定数量附件、必须同时拥有合同+发票+物流三件套 |
| `GOODS_PREPAY_V1` 合同预付款 | 付款在合同履约前、约定交期未到，且预付安排与背景相符 | 交易主体 → 合同预付条款 → 付款安排/对手核验 → 未来履约节点 → 持续跟进责任 | 尚未发生的交付证明；把未交付直接等同虚假贸易 |

配方不适用的例子：实际为贷款归还、关联资金调拨、平台代收代付而不是本企业货款。返回 `POLICY_NOT_APPLICABLE`，保留原始线索供人工研判，不能自动切到更宽松配方获取合理排除。行政用户也不能修改单案 policyCode 绕过适用性验证。

代付/代收不是自动可疑，也不是普通主体一致：增加 payer/payee 与合同主体的差异项，核对委托关系、付款安排、资金用途及来源记录。首批材料适配器能提供明确授权记录才可演示已解决；复杂多层代收结构保留为超出本配方能力的未知。

## 5. 六问题的“充分性配方”

每题保存 `assessment=SATISFIED/NOT_SATISFIED/UNKNOWN/NOT_APPLICABLE`、具体判断、事实定位、核验动作、局限和判断人。状态由人提出，服务端检查其适用条件和证据约束；系统不能独立证明人工判断真实。

| 问题 | 已交付结算需回答 | 预付款需回答 | 可接受核验/替代方式 | 重要阻断 |
|---|---|---|---|---|
| Q1 经营一致性 | 企业角色、货物、结算规模与日常经营是否相符 | 为什么需要预付，账期与采购模式是否相符 | 已核验业务背景、同类订单、具人员和时点的查访记录 | 客户泛化自述是唯一依据；重要背景矛盾未处理 |
| Q2 入款用途 | 付款人与买方是否一致；订单和收款是否对应 | 收入是客户订金、货款还是其他性质，是否确有依据 | 来源交易记录、订单、经核验代付安排 | 主体未知、代付关系无依据、相互冲突 |
| Q3 出款用途 | 收款人、采购及交付是否对应 | 预付条款、收款授权、交期是否明确 | 收款主体查验、合同记录、交付系统记录；无物流时可用有来源的验收/提货核验 | 把客户上传文本视为独立核实；收款人冲突未解决 |
| Q4 范围与对账 | 每笔命中交易怎样对应订单、金额和期间 | 本次预付占订单金额多少，余款/未来履约节点是什么 | 按交易唯一 ID 对账；原币种、分配合计及差异计算 | 遗漏命中交易、重复计额、超分配、未知源身份 |
| Q5 周转解释 | 为什么快速结算，收支差额属于什么 | 为什么需要同日预付，预付规模及风险如何被解释 | 结算条款、费用安排、客户经营约定与其他核验相互印证 | 用收支差额直接冒充利润；仅“正常经营”四字 |
| Q6 反证与未知 | 重要差异是否已解释、未知是否妨碍本次判断 | 未到期事项与已经逾期事项是否区分；后续谁查什么 | 问题处置记录、来源定位、未来跟进责任 | 静默忽略反证；用“待后续核验”掩盖当前关键未知 |

替代证据是替代核验方法，不是材料名称同义替换。比如“无物流单”可以由有独立来源的验收记录解释，也可能仍属未知；是否接受取决于具体事实、来源局限和问题要求。

### 5.1 将事实、陈述与推断分开

`DOCUMENT_ASSERTION`：文件记载“已发货”；`OBSERVED_FACT`：核验人在明确系统/方式中观察到对应交付记录；`ANALYST_INFERENCE`：据此认为本次付款具有货款性质；`UNKNOWN`：尚未核实实际签收。四者分别保存和展示，不允许模型将第一项升级成第二项。

来源状态采用两个维度：`availability=RESOLVED/UNAVAILABLE/NOT_FOUND/FORBIDDEN` 与 `integrity=MATCH/MISMATCH/NOT_CHECKED`。来源可查、哈希一致只说明内容可定位和一致，不自动授予“业务真实”。人工核验还需方法、观察结果、适用期间与限制。

### 5.2 时间上的关键区别

- 合同在交易发生日有效、核验日已到期：按交易适用期评价，不简单拒绝。
- 预付合同约定的交付日尚未到：可标 `NOT_YET_DUE`，有合同来源和跟进任务时不把缺交付材料当成当前缺陷。
- 交付日已过，仍无交付或合理延期依据：自动产生需要人处理的新问题；不得继续使用旧 `NOT_YET_DUE`。
- 页面定时显示到期不是事实生效机制；服务端评价时使用注入的 Clock、固定业务时区及日期规则，最终提交也重新检查。

## 6. 重要性、反证处置与补件停止规则

### 6.1 问题分类

| 等级 | 例子 | 对合理排除的影响 | 谁能处理 |
|---|---|---|---|
| `INTEGRITY_BLOCKER` 完整性/身份错误 | 跨案材料、内容哈希不符、范围记录缺失、撤销来源仍被使用 | 不得以被破坏的依据形成任何最终决定 | 修正来源/范围后重评；不能以业务文字豁免 |
| `DECISION_CRITICAL` 关键业务矛盾 | 收款主体冲突、核心用途未知、关键期间不符 | 阻断合理排除；可以作为人工怀疑分析的一部分，但不能假称已解决 | ANALYST 提出解决/影响判断，REVIEWER 核对 |
| `CONTEXT_GAP` 非关键缺口 | 与本次命中无关的辅助说明欠缺 | 只有明确解释“不影响本次决定”的理由和引用时可继续 | 有记录的分析与复核；不能默认降级 |
| `FUTURE_OBLIGATION` 尚未到期事项 | 合同约定未来验收、预付款到货复核 | 当前条件满足且已分派持续跟进时可继续 | REVIEWER 确认责任人、到期时间和核验目标 |

未评估的重要性默认按关键待处理项。降级必须记录原等级、理由、引用和不同复核人确认；INTEGRITY_BLOCKER 不允许降级。不能用金额很小作为忽略主体异常的唯一理由。

完整性阻断针对**拟被采用为事实的来源及范围**。发现客户所给材料与独立查验不一致时，可以将“收到的内容、实际计算结果及独立查验观察”形成新的可核验事实，保留争议原件及处置；不能继续把原声明当成已核实，但也不能因发现伪造迹象就永远阻止有可靠依据的可疑判断。修复的是采用依据及其表述，不能删除不利材料或将完整性错误改成无关项来绕过控制。

问题处置只能是 `RESOLVED_WITH_EVIDENCE`、`NOT_RELEVANT_WITH_REASON`、`DISCLOSED_UNRESOLVED` 或保持 OPEN。撤销任务与解决问题分开；新文件到达也不自动关闭问题。

### 6.2 避免无限补件

每项请求写明“要解决哪个问题、为什么现有材料不足、可接受哪些替代核验、责任人、截止点”。重复相同缺口且没有新核验路径时，提示复核人做方向选择，不自动再生成相同任务。

演示政策：首次请求截止 2 个工作日；第二轮仍无进展或首次到期时升级给 REVIEWER；这些只是可配置演示默认值，非法律时限。保存 `calendarVersion`，不同工作日历不得改变历史截止时间。

升级后的选择：更换可行核验方法；记录有依据的非关键性；认定当前不能支持合理排除而保留人工调查；或依据已有已评估事实进入可疑判断。到期不会自动判可疑、自动排除或自动结案。紧急疑点可立即送复核，不必等演示截止时间。

## 7. 不对称的最终决定规则

### 7.1 预警单元建议

- `EXPLAINED`：适用配方满足，范围完整，解释有已记录的适用核验，关键矛盾已处理，依据当前有效。
- `SUSPICIOUS`：分析员明确记录支持合理怀疑的已评估事实、反向解释及为何仍不足以消除疑点；解释“不满足”本身不够。
- `UNRESOLVED`：尚无充分解释，也未形成足够的人工怀疑分析。保留未知，不二选一凑结论。

### 7.2 案件层决策表

| 当前组合 | 可建议最终排除 | 可送最终确认可疑 | 必须显示的事实 |
|---|---|---|---|
| 全部单元 EXPLAINED，其他场景门禁也满足 | 是 | 否 | 全范围说明、未到期跟进事项（如有） |
| 部分 EXPLAINED、部分有依据的 SUSPICIOUS | 否 | 是 | 逐预警不同结论，不能把正常部分改成可疑 |
| EXPLAINED + UNRESOLVED，没有有依据的 SUSPICIOUS | 否 | 否 | 具体未知与下一步调查 |
| 有依据的 SUSPICIOUS + 已披露 UNRESOLVED | 否 | 条件满足才是 | 未知的位置、与可疑依据的关系、继续跟进任务和责任 |
| 只有“解释受挑战”，没有人工怀疑事实 | 否 | 否 | 不能通过反向逻辑自动认定可疑 |
| 当前依据完整性错误、过期或范围未枚举 | 否 | 否 | 修复/重评具体入口，不把缺失事实编入报告 |

“可送最终确认可疑”仍需具有权限且不同于该提交所有实质贡献人的 REVIEWER 作最终决定。本表不把业务判断自动化；它检查建议及依据是否具备可复核条件。

### 7.3 对当前 v1 强耦合的明确修改

当前 `InvestigationService.updateCoverage()` 和 `InvestigationReadinessEvaluator` 将 EXPLAINED 绑定到整个假设 REJECTED；前端 `utils/investigation.ts` 也依赖此口径。v2 本场景应改为校验**预警单元不可变提交及其依据**，不再根据汇总假设状态推算每条覆盖方向。

v1 案件保持旧语义。v2 RAPID_MOVEMENT 的覆盖增加 `unitSubmissionId`，最终校验必须存在且属于当前 alert/case/policy；SUSPICIOUS 与 EXPLAINED 分别匹配该单元建议。未解决事项在已有覆盖中可保持 PENDING，但只在确认可疑时允许被显式的 `DISCLOSED_UNRESOLVED` 处置记录采用；不能把它改写为 EXPLAINED。

其他场景仍执行原门禁，不能在 v2 分支整体跳过调查校验。兼容分支按受支持的契约/政策白名单选择；未知版本拒绝写入，不以 `version >= 1` 等同全部新契约已支持。

## 8. EDD 与报送的接续规则

### 8.1 为什么必须修改现有流程

现有 `EnhancedDueDiligenceService.validateReviewDecision()` 会阻断有 OPEN EDD 的案件再次处置，`submitResponse()` 只允许 HOLD，`applyReviewDecision()` 还会将最近 SUBMITTED 任务自动 RESOLVED。因此仅写“保留未知继续研判”无法实现完整流程。

### 8.2 复用任务结构，分清目的

增加任务 `purpose=DECISION_SUPPORT/CONTINUING_REVIEW`，保持原状态 OPEN/SUBMITTED/RESOLVED/CANCELLED。DECISION_SUPPORT 是当前判断需要的补件；CONTINUING_REVIEW 是已经分派、可在本轮决定后履行的未来核验或披露未知的继续调查。

**不把原 OPEN 任务静默改名为完成。** REVIEWER 决定在有已披露未知时确认可疑，应在同一事务里：

1. 确认有可复核的怀疑依据，列出每项仍未知内容及其对本次判断的影响。
2. 为需要继续核验的内容创建 CONTINUING_REVIEW 任务，记录原 requestId/issueId、责任人、到期点、完成标准及必要的材料上下文。
3. 将已转移义务的原任务标为 CANCELLED，原因码 `SUPERSEDED_BY_CONTINUING_REVIEW`，保留原轮次、未解决问题和新任务 ID。不能标为 RESOLVED。
4. 完成现有最终复核、进入 REPORT_PENDING；审计 Outbox 或任一任务写入失败时整体回滚。

任务接续同样适用于预付款中的未来履约检查，但只有 `FUTURE_OBLIGATION` 可在合理排除时接续；当前关键未知不得借 CONTINUING_REVIEW 放行排除。

### 8.3 决定后仍能履行的工作

- CONTINUING_REVIEW 必须出现在原承办人队列；允许在 HOLD/REPORT_PENDING/DONE 按任务权限提交材料，前提是任务仍 OPEN。这一权限只写任务与补充材料，不开放已结案假设、覆盖或最终决定编辑。
- 后续核验由不同复核人明确完成任务；不再因“最近一轮”被其他业务决定自动 RESOLVED。DECISION_SUPPORT 的处置也需显式 requestId/expectedRevision，避免消费错轮次。
- 记录外部受理编号仍可按既有报送流程进入 DONE；页面解释 DONE 是该报告/本轮决定结束，持续跟进仍单独显示，不能从队列消失。
- 后续出现重要新疑点或原排除依据被否定，建立有来源的后续案件建议；需要新案件时沿现有 intake 建立并关联旧决定，不重写原档案。首批不做外部自动事件采集，仅支持当前任务提交或授权人工登记。
- 如果无法创建有承办人和截止点的接续任务，当前系统不允许假装已完成义务并提交该分支。

## 9. 状态设计：草稿、提交、复核互不覆盖

| 对象 | 状态/版本规则 | 行为 |
|---|---|---|
| 单元草稿 | `draftRevision` 乐观锁，可编辑 | 自动保存只改变草稿，不生成最终业务判断 |
| 单元提交 `UnitSubmission` | 不可变；具有提交 ID、依据摘要、作者集合 | 一次人工提交冻结问题、事实、材料、未知与建议 |
| 提交适用性 | CURRENT/WITHDRAWN/STALE/SUPERSEDED，以事件与当前指针表示 | 不修改已冻结 payload；最终决定只能采用 CURRENT |
| 最终复核 | 引用本次采用的提交 ID 集合与 ReviewBasis | 保留 reviewer、决定、理由、版本和未解决项处置 |

`POST /units/{unitId}/submissions` **一次原子动作**校验本单元全部输入，创建不可变提交、写当前覆盖/单元结论、更新假设汇总并登记审计。取消 v1 方案中“先提交整假设排除、再手动逐预警确认覆盖”的多步模式，消除中间版本自相矛盾。

单元为 UNRESOLVED 也能提交当前调查结果供人查看，覆盖保持 PENDING，不是假定它已经可以被最终决定采用。未提交草稿永远不能满足门禁。

再次修改已有 CURRENT 提交，先显式执行 amendment：撤回当前提交、创建下一草稿、推进案件事实序号。界面提示该操作会使待复核依据失效；仅在浏览器里打字没有服务端效果。旧提交仍可回放，但不能继续被最终决定采用。

实质贡献人集合包括创建解释、编辑判断、解决关键矛盾、形成核验结论的人。只比较“最后点击提交的人”不足以阻止自审；最终 reviewer 不得属于本次采用提交的实质贡献人并集。角色切换和 ADMIN 都不豁免；合成演示至少使用两个实际用户 ID。

贡献人由服务端从追加的操作记录及复用内容来源派生，不接受客户端自报空集合。复核员退回问题属于复核动作，不自动算成其编写了分析；若复核员直接改写判断、解决关键矛盾或形成被采用的核验结论，则该版本需另一个人最终复核。

## 10. 版本与原子性：减少无效冲突，堵住旧入口

### 10.1 三类版本

1. `draftRevision`：只用于编辑一个草稿。
2. `caseFactsEpoch`：案件当前事实变更序号；范围、材料有效性/核验、当前提交、关键问题处置、政策绑定及任务义务变更时推进。
3. `submissionId + inputDigest`：一次不可变人工提交；摘要包含固定排序后的范围、问题、材料/核验版本、政策和声明未知。

最终页面只提交服务端返回的 `reviewBasisToken`，不要让浏览器自行拼五六个版本。服务端将 token 绑定到 caseId、caseFactsEpoch、当前采用提交、任务义务和政策摘要；在案件锁内比较当前事实。令牌不是身份凭据，也不能替代权限校验。

### 10.2 失效范围

已使用材料变化：按反向引用定位受影响单元，将这些提交 STALE；案件 token 变化。其他单元的有效提交可以复用，复核人查看差异后取得新 token，不必重填全部问题。

新材料尚未关联单元：写入案件待分派事实清单，并推进 epoch；最终决定前需有明确关联或有理由的不相关处置，不能靠“不引用它”规避反证处理。只改文件显示名等白名单非实质字段不会推进依据版本。

时间越过预付款履约点时，最终提交即时重新评价，不依赖定时任务是否准时执行。已完成决定按当时 evaluateAt 回放；新的逾期事件影响持续任务，不改写当时结果。

### 10.3 锁与幂等

业务事务锁顺序固定：案件 → 涉及假设按 ID 升序 → 单元/当前指针 → 覆盖 → EDD 任务按 ID 升序。来源抓取在事务外进行，入库时短事务复核版本与状态。最先获得案件锁并成功提交的写入构成顺序；不宣传已经获知尚未到达本系统的外部变化。

幂等键包括动作、操作者、目标资源和请求摘要。同键同请求返回原提交 ID，同时重新给出该提交的 CURRENT/STALE 状态；重放不新增版本、不自动重新应用旧内容。同键不同请求返回 409；权限先于幂等缓存结果校验。

旧 `addEvidence/updateHypothesis/updateCoverage` 对启用本政策的资源必须委托同一业务服务或明确拒绝；不能在旧的“状态和文字相同”幂等返回分支前漏掉依据有效性检查。后台管理和批处理同样走此边界。

## 11. 交易与材料的数据约束

### 11.1 冻结交易

新的带身份交易至少有 sourceSystem、sourceRecordId、sourceRecordVersion、customerId、accountId、counterpartySubjectId、bookedAt、direction、amount、currency、postingStatus 和 reversalOf。当前关系适配器已有本地交易 id/sourceUpdatedAt，可透传，但不能声称是核心银行全局流水号。

旧 `TransactionRecord` 保留；同一次 SourceCapture 产生旧视图与新的可定位事实，核验依据独立归档并绑定原案 snapshotId、源截止点和源版本。新增事实不回填旧快照，不改变旧 sourceDigest 的算法意义。

旧归档数组位置只能定位该归档记录；没有源 ID 时不自动与实时流水合并。一次 sourceRecordId 出现不同版本时选择本次冻结截止点允许的唯一版本并保留选择规则，不能将更新前后两行都算为两笔业务交易。

### 11.2 金额、关联与冲正

- 金额使用 Decimal；API 传定点字符串如 `"320000.00"`。CNY 以两位小数校验，首批其他币种显示不适用，不换算凑合。
- 同笔资金可以有多份材料佐证，但金额只计一次。订单金额分配与证据佐证关系是不同对象；单一分配维度内合计不得超交易金额。
- 首批订单分配误差为 0.00；费用、退款、折让用独立有依据的调整项表达，不用隐藏百分比容差消除差异。这是演示政策，不是银行通用阈值。
- 成功入账记录与冲正按明确关联处理；保留原始和净额口径。未知记账状态不默认成功；同刻同额但不同源 ID 保留多笔。
- 出账/入账=96% 仅为观察值，入账合计减出账合计不叫利润；不能仅凭时间和金额声明两笔属于同一资金链。

### 11.3 材料证据

抓取只接受已配置 sourceSystem 和不透明引用，不接受任意 URL。保存实际取得内容的哈希、claimedHash、来源链、原文定位、源版本、取得时间和适用期间。相同来源转发件不能算独立核验。

关键材料撤销和正文变更只追加版本/事件；核验记录也追加。不能在引用指向最新版本的同时继续展示旧人工核验结果为当前有效。

## 12. 数据模型收敛

首批采用关系表保存需要联查和施加约束的关系，固定六问题保存在提交 payload 内；避免同时维护可变问题表、提交副本及通用规则引擎三套事实。

| 表/对象 | 主要内容 | 关键约束 |
|---|---|---|
| `verification_basis` | caseId、basisRevision、冻结交易/客户事实密文、来源截止点、scopeDigest、basisDigest | 追加版本；不能被原案最新快照指针静默替换 |
| `evidence_artifact_version` | caseId、artifactKey、version、sourceRef、内容定位/密文、实际 hash、期间、来源链 | 同案 artifact/version 唯一；正文不可更新 |
| `evidence_verification_event` | artifactVersionId、method、observedFacts、limitations、result、actor、time、previousEventId | 追加；技术解析与人工作用判断分开 |
| `alert_explanation_unit` | caseId、alertId、hypothesisId、policyCode、scopeRevision、草稿密文、draftRevision、currentSubmissionId | 同案 alert 唯一；当前指针更新受案件锁保护 |
| `explanation_submission` | unitId、submissionNo、冻结六问题/建议/未知/贡献人、basisId、inputDigest、submittedAt | 不可变 payload；唯一 unit/submissionNo；状态变化通过事件记录 |
| `explanation_evidence_use` | submissionId、questionCode、artifactVersionId、verificationEventId、定位、transactionIds、effect | 全部同案；显式版本；用于受影响单元反查 |
| `explanation_issue` | 稳定 issueId、单元或案件、等级、处置、revision、来源、处理依据 | 待分派新材料也能挂案件；不可静默删除 |

解释方向仍为 SUPPORTS_EXPLANATION/CHALLENGES_EXPLANATION/CONTEXT，与风险假设的 SUPPORTS/CONTRADICTS 不混用。

复用现有 EDD 表增加 purpose、originRequestId、originReviewId、issueBindings、dueCalendarVersion、resolutionReason；任务轮次仍在案件内唯一，查询按目的和实际 ID，不再假设“最近一轮就是要消费的一轮”。

复用既有审计事件/Outbox 保存提交状态事件、失效和实质贡献记录；只保存审计日志中的一句话不足以还原状态，需定义可查询的结构化业务事件字段。最终 ReviewBasis 的完整采用清单随人工复核记录/档案冻结。若现有审计实体不适合充当业务事件存储，实现时增加专用状态事件表，不能为了维持七张表的数量而依赖易失日志。

## 13. API 与用户操作协议

前缀 `/api/cases/{caseId}/investigation`。以下都是拟新增/扩展接口。

| 接口 | 作用 | 前置条件/输出 |
|---|---|---|
| `GET /verification/workspace` | 返回全部预警单元、范围、六问题、待分派材料及阻断项 | 同时返回各单元能力及当前 caseFactsEpoch；全量范围不受页面筛选影响 |
| `POST /evidence/captures` | 抓取受控材料 | 不透明来源引用+幂等键；返回待核验结果，不叫已证明 |
| `POST /evidence/{versionId}/verifications` | 记录具体核验 | 方法、观察、限制、预期依据；服务端检查人员权限 |
| `PUT /units/{id}/draft` | 保存六问题草稿 | expectedDraftRevision；不能顺带产生最终结论 |
| `POST /units/{id}/submissions` | 原子提交本单元建议和当前覆盖 | 草稿版本+观察依据令牌+幂等键；返回 submissionId 与当前汇总 |
| `POST /units/{id}/amendments` | 撤回当前提交，开始修改 | 当前 submissionId；推进 epoch，保留旧提交 |
| `POST /issues/{id}/dispositions` | 解决、说明不相关或披露未解决 | expectedRevision、处置理由/证据；重要性降级需复核确认 |
| `POST /edd-proposals` | 分析员提出按问题补件建议 | 不产生 REVIEWER 权限；建议进入待处理复核队列 |
| `GET /review-basis` | 为最终复核取得冻结候选依据 | 返回采用单元、未知、任务义务、canExclude/canConfirm、token |

最终复核沿现有接口，只增加 reviewBasisToken、采用单元清单及 continuationPlan，不增加第二个能独立写 DONE 的接口。任务接续由服务端复核事务内部创建。

响应中的阻断结构统一：`code、severity、unitId、questionCode、issueId、transactionIds、message、allowedActions`。前端依据 allowedActions 展示入口，但后端每次重新校验。例：Q3 主体不一致返回 `PAYEE_MISMATCH/DECISION_CRITICAL`，可行动作是补证、记录核验或提交疑点分析，不是“忽略错误”。

## 14. 页面：围绕问题办事，避免重复录入

工作区首先显示“本案 3 条预警：1 条有解释、1 条有疑点、1 条未决”，而不是一个模糊的完成百分数。点击单元进入六问题，交易—订单对账和材料抽屉相邻展示。

已存在材料按问题推荐复用；系统保留来源和核验局限，要求人确认本次适用性。允许一份材料回答多个问题，自动带入同一定位；不同问题的人工结论不能随材料复用自动完成。

关键问题列表始终可见；“申请补件”自动带出尚缺事实及可接受替代方式，避免让分析员再抄一次。预付款单元显示履约时间线，未到期事项与逾期问题采用不同标签。

复核页提供：本次建议 → 各预警差异 → 支持与反向信息 → 当前未知 → 已安排任务 → 最终动作。正文按需展开；业务页面不要求用户理解摘要算法或数据库锁。

草稿服务端显式保存可跨刷新恢复；客户端只保存本次编辑状态，不默认长期落盘敏感正文。成功写入后刷新失败沿用 A4-01 的处理：提示已保存、旧事实不可继续使用、重载不重放。收到 409 给出具体变化并保留草稿。

## 15. AI 的有限增益与拒答

AI 只在人工闭环稳定后接入。输入是本案冻结范围、可解析材料、配方和六问题；输出候选回答、支持/反向定位、未知和建议核验动作。服务端校验其引用属于输入集合，并将人物、金额、日期与结构化事实核对。

模型建议“可能是代收”不等于代收成立；候选直接进入待确认区域。模型必须能输出“现有材料不能回答 Q3”，不能以补全段落为成功目标。

先只增加两项功能：定位相关材料并列出缺口；依据已确认结构化工作单草拟复核摘要。暂不引入自动调查多 Agent、自主外部查询、学习型风险评分或连续自动决策。

记录 modelVersion、promptVersion、输入依据、候选内容、采纳/拒绝原因和人工差异。模型不可用时，材料核验、提交、EDD 和复核均可完成。

| S1 事实与核验 | 范围、交易身份、材料解析、核验、七类核心对象和六问题人工草稿 | 7–9 | 只读/观察及演示，不得独立打开最终 v2 处置 |
| S2 单元提交与复核 | 原子提交、汇总、混合覆盖、token、自审与历史、旧入口守卫 | 7–9 | 尚需 S3，避免上线可疑路径因 EDD 不可履行而卡住 |
| S3 EDD 与接续 | 补件建议/升级、目的分离、决定后提交、任务接续事务、队列联动 | 5–7 | 与 S2 共同构成完整人工闭环 |
| S4 界面/档案/回退 | 工作区与复核页、定位和差异、完整档案、新旧契约保护 | 5–7 | 配合 S5 才能启用试点写入 |
| S5 故障及角色验证 | 本文反例、真实 MySQL 并发、Outbox 回滚、角色 E2E、回退演练 | 4–6 | 全部硬门槛通过；人工闭环合计 30–41 人日 |
| S6 AI 与效果对照 | 两项 AI 辅助、固定案例比较与拒答测试 | 3–5 | 可选，不阻塞已验证人工闭环 |

这是建议估算，未包含真实机构系统、第三方材料服务和领域专家排期。S1 先给出可见进展；S2–S5 未完成时只标注观察/开发版，不宣传具备完整核验闭环。

### 17.2 迁移和回退

新增 Flyway 迁移使用实施时未占用版本，既有 V25/V26 不修改。旧证据继续标记历史未解析引用，旧案不自动升级为已核实。v2 试点必须显式开启、冻结政策，现有 v1 案件继续原语义。

回退策略优先停用 AI、暂停新建 v2 案件，保留 v2 人工处置及持续任务。旧二进制若不认识 v2 必须拒绝写入；不得退回“只检查 version >= 1”的逻辑后继续办理 v2。已生成持续任务不能因前端回退而失联。

材料完整性问题、引用越权、依据失效未阻断、任务转移部分提交、自审绕过为停止试点写入的条件；停止新建案件与停止既有持续跟进分开控制，确保已分派义务仍能履行。

## 18. 验收：把容易漏掉的反例先固定

保留 v1 中原始来源解析、哈希、同源材料、时效、金额、冲正、权限、故障等测试意图；**与 v2 相冲突的旧状态断言必须重写**，尤其不能再断言所有 EXPLAINED 都要求整假设 REJECTED。

| ID | 反例或关键步骤 | 正确结果 |
|---|---|---|
| V2-01 | 已交付结算且六问题有适用核验 | 可提出 EXPLAINED，不同贡献集合外复核人可排除 |
| V2-02 | 合法预付，交期未来，已安排核验 | 不要求未来交付单；可说明当前解释成立及后续义务 |
| V2-03 | 与 02 同事实，但交期已过且无合理延期 | 产生当前关键问题，不能沿旧依据排除 |
| V2-04 | 一预警合理、一预警有支持怀疑的事实 | 覆盖分别 EXPLAINED/SUSPICIOUS，汇总 CONFIRMED |
| V2-05 | 合理+未知，没有支持怀疑的事实 | 两种最终决定均不放行，显示补证/人工调查 |
| V2-06 | 可疑+未知，未创建义务接续 | 不以口头“以后查”完成最终确认 |
| V2-07 | 可疑+已披露未知，明确任务接续 | 原任务非 RESOLVED；事务成功后可确认，任务继续可办 |
| V2-08 | 只有解释不成立，未记录怀疑依据 | 不自动产生 SUSPICIOUS |
| V2-09 | 为通过门槛删除命中交易或切换宽松配方 | 服务端拒绝，范围及适用性仍待处理 |
| V2-10 | 同交易关联两条预警 | 案件金额不重复计，预警解释不自动相互继承 |
| V2-11 | 引用来源存在但内容被换、或源记录版本冲突 | 不能沿用旧核验，列出受影响单元 |
| V2-12 | 新材料不关联任何单元 | 进入案件待分派，不可用“不引用”绕过处理 |
| V2-13 | 修改已提交工作单 | 先撤回、后改稿；旧提交可回放但不可最终采用 |
| V2-14 | 提交成功，刷新失败，再次点击 | 不重放写入；显示已保存及失效/重载状态 |
| V2-15 | 当前 token 与新证据提交并发 | 案件锁内只有基于一致事实的结果；旧 token 被拒绝 |
| V2-16 | 义务转移、最终复核中的审计登记失败 | 任务/状态/决定全部回滚，不出现孤儿义务 |
| V2-17 | 父案报告登记后 DONE，持续任务仍 OPEN | 原承办人可以按任务提交，不能编辑旧最终决定 |
| V2-18 | 原作者换另一个提交人，再以 reviewer 身份自审 | 实质贡献人校验仍拒绝 |
| V2-19 | 普通辅助缺口被降级，但没有理由或独立确认 | 仍阻断，不能只改 severity 字段 |
| V2-20 | 第二次相同补件，仍无新路径 | 展示停止重复/升级选择，不自动再发同一要求 |
| V2-21 | 抓取时合法，落库前案件已决定 | 不修改旧依据；按决定后任务/变更登记路径处理 |
| V2-22 | 重放旧幂等请求，此时原提交已过期 | 返回原 ID 和当前 STALE，不创建“新鲜”提交 |
| V2-23 | 旧 API、管理员或批处理直接改覆盖 | 同一 v2 守卫生效，无旁路 |
| V2-24 | v1 旧案、未知契约 v3、关闭 v2 开关 | 旧案按旧规则；未知版本拒绝写；已有持续任务仍可处理 |
| V2-25 | AI 引用存在但把“合同称已发货”写成“已核实发货” | 不能直接进入 OBSERVED_FACT，要求人工核验 |
| V2-26 | 系统把所有测试案例都拦住 | 合法解释放行指标失败，不能因错误放行率为 0 而验收通过 |

使用 [设计一致性检查脚本](examples/check-rapid-goods-v2-plan.mjs)可复查 21 个明确案例，以及方向互斥、顺序不敏感和关键门禁关闭时不得放行的约束。输入中的“事实可用”“分析有效”等布尔值是被测设计的前提，不是该脚本对材料真实性的核验结果。运行命令：`node docs/plans/examples/check-rapid-goods-v2-plan.mjs`。实现阶段必须由真实接口、数据与操作者产生这些前提，并补齐第 18 节集成场景。

## 19. 效果指标：防止用保守或流畅的输出冒充改进

建立 72 个独立合成案件，36 DEV/36 固定 TEST；各集合至少 12 个可合理解释、12 个需要继续核验、12 个有人工怀疑依据的场景，涵盖两配方、混合预警及来源异常。客户/订单家族在切分时保持同侧；同一故事仅换姓名不能跨集合。

使用成对变化：相同资金流改“交期未到/已过”“来源可查/不存在”“收款身份相符/矛盾”“反证已处理/未处理”；只有相关问题和允许动作应变化。再验证材料顺序、措辞、文件名变化不应改变结构化结论。

| 指标 | 分母与判定 | 目标/使用方式 |
|---|---|---|
| 错误排除放行 | 标注不可排除案例中，系统可实际完成排除的比例 | 硬反例为 0；检查接口和最终状态，不能只看按钮 |
| 合法解释误阻断 | 标注可排除且权限/材料条件齐备案例中，被系统不合理阻断的比例 | 固定金标应为 0；由此识别“全部阻断”方案 |
| 未知被强行定性 | 需要继续核验的案例中，被自动改为可疑或排除的数量 | 0；缺信息不等于风险已定性 |
| 关键反证遗漏 | 标注关键反证中，既未提示也无处理记录的数量 | 确定性样例 0；不是只测类型字段存在 |
| 引用与表述忠实性 | 已提交事实中，定位有效且表述未超出材料/核验记录的数量/总数 | 报告两个子指标，不用引用可解析率替代语义核对 |
| 复核劳动 | 每案人工操作时长、重复请求数、材料重复录入数 | 与结构化人工基线比较，不以等待外部材料时间包装 AI 效率 |
| AI 净帮助 | 定位正确率、缺口建议采纳、错误新增事实、修订量及延时 | 人工闭环 vs 加 AI；无稳定收益则不启用该辅助 |

72 个案例不能证明真实银行效果。没有领域评审时标记开发者合成预期；合法/可疑标签是处置建议范围，不是司法结论。效率先采集基线；20% 提升仅可作为实验假设，不作为已经达成的结果。

## 20. 可以开始实施前的退出条件

开始 S1 前：两配方样例、范围契约、六问题判断含义和新旧 API 差异已冻结。开启 v2 最终写入前：混合覆盖、未解决事项、任务接续、自审、旧入口守卫、回退和真实事务测试全部通过。

产品演示至少展示四段连续操作：合法已交付结算；合法预付款及未来履约；同案部分合理部分可疑；已形成建议后收到新材料并触发重评。最后回放旧决定与仍在办理的任务，让用户能看见本次决定结束与持续尽调责任之间的区别。

本版最终要证明的能力是：**一条预警为何能解释、另一条为何仍有疑点、哪些事实尚未知、谁在何时继续查、当时的决定如何被重现。**
