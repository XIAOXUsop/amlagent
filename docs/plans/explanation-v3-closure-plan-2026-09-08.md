# 下一步方案：完成 v3 的来源、授权、义务闭环

日期：2026-09-08。基线：`9199924`。状态：计划，未实施。

依据：[本轮再次验收报告](/D:/JCode/docs/reviews/explanation-v3-reacceptance-2026-09-08.md)。业务范围继续沿用 [代付专项 v3](/D:/JCode/docs/plans/third-party-goods-payment-verification-plan-v3-2026-09-08.md)，本轮不增加跨境、个人代付或新的自动判断模型。

## 1. 下一步的明确目标

完成一条可以在真实隔离数据库上执行的路径：**权威交易范围 → 可定位核验事实 → 授权逐笔覆盖 → 单元建议 → 独立复核 → 义务接续 → 历史档案**。

验收基准不再是“新增了哪些实体和接口”，而是以下输入变化都能得到正确响应：删除证据、删去授权、缩小覆盖集合、核验结果撤回、跟进任务缺失、来源不可用、补件请求从页面发出、并发修改依据。

先恢复现有路径的正确性，再补全代付链。默认回归通过和单元级首批交付不能作为开放最终排除的充分依据。

## 3. R1：先使正常请求与异常来源都能按预期落地

### 3.1 补件令牌协议

采用明确分工：最终确认/排除继续强制 basisToken；REQUEST_ENHANCED_DUE_DILIGENCE 保留案件锁、expectedReviewRevision、角色和任务状态检查，豁免“最终依据 token”。它的用途是补齐尚不足的调查，不能要求先具备最终处置条件。

修改 ReviewService 的前置 token 分支并补 ReviewView 请求契约测试。三种决定各测一次成功请求、一次版本冲突；最终决定空 token 仍应拒绝，不能为修补件路径全局放松 token。

### 3.2 来源状态与摘要

短期复用 EvidenceArtifactVersion：未取得内容的状态允许 contentSha256=null；RESOLVED 必须具有服务器计算的摘要。实体约束与新增 Flyway 迁移同时变更，不能只改单侧，也不能给空来源补伪造摘要。

新增迁移编号在实施时检查仓库后确定，保留 V27 校验和。数据库测试覆盖首次 NOT_FOUND、UNAVAILABLE、FORBIDDEN、之后来源恢复，以及同源内容变化。检查数据库行、问题记录和审计事件，不能只断言返回 DTO。

## 4. R2：让“有依据”成为可核实条件

### 4.1 事实采用规则

将现有草稿 claims 与 ExplanationClaim/ClaimEvidenceLink 的实际写入链补齐。一次提交冻结 Claim 版本、支持及反对的材料版本、核验事件、事实位置和人工理由。业务判断可由人提出，技术可用性由服务器验证。

规则至少包含：

- 关键 Claim 不允许仅凭 SUPPORTED 字符串成立；必须存在满足该用途的引用和核验记录。
- 引用属于本案件/合法授权范围，位置属于相应内容版本；来源取得状态、完整性和核验适用性满足要求。
- 无材料的草稿可保存为未完成调查；不得凭 CONTEXT 占位使用记录升级为可采用 EXPLAINED。
- 同源文件副本、转发与摘要不能累加成独立确认；来源家族按原始签发/取得链记录。
- 关键未知保留阻断；非关键例外必须有可回放的理由及所需独立确认，不能让用户自由勾选“不适用”跳过核心事实。

### 4.2 冻结正确范围

实现 AlertScopePort 或等效服务器映射：冻结 alertId 对应的完整触发交易 ID、辅助交易、源版本和金额。现有“该交易属于客户全部交易”只证明存在性，不能证明它解释的是该条预警或已经解释全部命中交易。

范围无法枚举时保留明确 blocker，允许记录 UNRESOLVED 调查现状，禁止用文字解决范围完整性。提交验证与 VerificationBasis 持久化使用同一份已取得的事实快照，避免验证一次、保存时再次读取出另一份交易数据。

### 4.3 核验变更和失效

将材料更新、核验更正/撤销/UNRESOLVED、主体归属变化和问题处置统一送入依赖评估。使用关系绑定具体 verificationEventId，而不只绑定 artifactVersionId。

若采用事实失去支持，对依赖单元产生 STALE/待复核状态；无依赖单元保留。追加反证尚未分派时以案件清单阻断。最终事务检查依赖有效性，不能仅假定异步事件已经处理。

## 5. R3：把授权与每笔真实付款对应起来

先由服务器确定“哪些交易需要代付解释”，再验证授权覆盖。不得从客户端 coveredTransactionIds 反向定义需要解释的全集。

授权记录至少包含：可定位授权版本、授权方主体、代付方主体、收款方主体、适用订单/债务、币种、额度、付款时有效期间、撤销/替代关系和核验引用。首期不支持的复杂授权进入不适用或待核验，不切换宽松配方。

计算顺序：

1. 根据已核验主体关系确定代付资金腿；普通采购支出和手续费不混入代付授权使用量。
2. 对每笔资金腿找到有效授权及订单/义务分配，确认主体和时点匹配。
3. 找出未覆盖交易及部分未覆盖金额，保留具体缺口；不能因其他款项已解释而消除。
4. 按唯一分配核对授权累计使用量；共享交易命中多个预警时复用解释引用、去重计量，不能直接把共享引用判成异常。
5. 与 C3/C4 的人工建议比较；结构化事实不足时拒绝 EXPLAINED，不把不足自动认定为可疑。

标准反例固定为：T-1001=320,000.00、T-1002=120,000.00；授权额度 320,000.00 且只覆盖 T-1001。结果必须显示 T-1002 的 120,000.00 未解释。删除 authority、limitAmount 或 coveredTransactionIds，都不能让该反例变成可排除。

## 6. R4：每一项未完成责任都要有承接

从当前采用单元和问题提取 obligationId、目标事实、完成标准和期限，服务器逐项匹配继续任务。至少验证同案件、同义务、有效承办人、明确期限、仍可履行的任务状态。任意一条 CONTINUING_REVIEW 不能覆盖整个案件。

增加只读复核预检，输入 token、决定和拟议计划，输出覆盖差异与阻断；页面可编辑具体计划。最终复核仍在原有唯一入口完成。

事务顺序：案件锁 → 校验变更前 token/复核版本 → 即时重算事实与时间 → 校验计划覆盖 → 保存复核及承接关系 → 更新案件与任务、写审计 → 提交。任何失败整体回滚。新任务保存实际 originReviewId，不能一直传 null。

排除只允许承接纯未来履约义务，不能把当前决策支持缺口转换成未来任务。确认可疑可依法定业务流程保留明确披露的未知和后续责任；此处沿用既有人工报告流程，不新增自动报告动作。

## 8. 交付门槛与范围控制

R1 完成表示两条协议/落库问题已恢复；R2～R4 完成表示服务层关键逻辑闭合；RC-01～14 真实验证完成后，才将业务闭环标记为验收通过。

每个修复 PR 附上“此前错误输入 → 修复后的期望 → 实际运行结果”。把本次特征测试改为拒绝/失效/正确落库断言，并保留对应的正常业务成功样例，防止通过一律拒绝请求让测试变绿。

已终结案件保留原历史；存量无证据或无授权结构的 CURRENT 提交不自动认定满足新条件，按受影响清单重新核验。开关关闭时保留读取、导出和持续任务履行，不删除已产生的业务事实。

在上述门槛完成前，后续 AI 提取、新关系图和更多付款配方继续后置。下一步最有价值的成果，是把现有代付样例完整且可靠地跑通。
