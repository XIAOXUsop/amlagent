# Agent 测试集 v3 与项目验证充分性

## 1. 结论：工程回归与模型能力验收必须分开

原有 45 条不能充分验证整个项目。新增条数也不自动解决这个问题：

- 部分案例相关，配对和同模板变体不等于独立生产样本。
- 上一轮主要检查标准答案与校验器是否兼容，没有完整覆盖模型接口、并发工具、报告解析和最终评分之间的组合行为。
- Agent 数据不能替代工作流、鉴权、RAG、客户助手、数据库和浏览器用户旅程测试。
- 所有公开标签仍待领域专家复核，没有正式专家审批的隐藏 TEST，也没有新版真实模型成绩。

本轮将公开尽调集扩展至 90 条，并用进程内脚本模型让每一条实际走过 Agent 的工具循环和每案例评分。
这显著改善开发期回归覆盖；**仍不足以证明真实模型质量、法律判断正确性或银行生产可用性。**

高风险不等于所有情况自动冻结，冻结仍只在本项目合成一级名单控制中成为必需动作。

## 4. 完整执行链测试

`AgentEvalRunnerWorkflowTest` 使用不含 API Key、网络客户端或供应商连接的脚本模型，
通过生产共用的 `DueDiligenceAgentFactory / AiServices` 执行实际工具调用：

```text
脚本工具请求
  → 并发执行四工具
  → 验证模型第二轮确实收到本案例四份结果
  → 结构化报告解析
  → 冻结证据同步
  → 生产输出契约
  → 已有护栏与最终报告组装
  → 工具/证据/发现/动作/风险评分
```

90 条逐条检查调用、工具参数、结果内容、证据覆盖与任务通过条件。
该测试直接调用每案例执行单元，配置仍为 mock，不绕过公开真实评测的模型门控，
不写出“真实模型”评测报告，也不将脚本返回的标准答案冒充推理成绩。

额外故障回归覆盖：

1. 漏调名单工具，即使答案正确也不能通过任务。
2. 调错客户不会取得 fixture，后续重试成功仍保留错误参数记录。
3. 重复检索法规可完成任务，但 strictPass 因重复调用失败。
4. 工具执行失败必须记录 `success=false`；参数合法不代表采集成功。
5. 非法法规 query 不能靠模型自述补出证据。
6. 非法 JSON、未知动作、伪造 evidenceId、身份信息泄漏必须失败。
7. 模型传输失败保留在指标分母与高风险召回漏报中。
8. 无限调用工具受既定轮次上限约束。
9. 护栏救回错误的原始风险时，任务结果与模型原始失败分别记录。

参考答案被预先放入脚本模型，所以这只能检验工程链路与评分行为。
法规引用指标经过确定性补齐，表示最终报告可追溯性，不是原始模型独立引用能力。

## 5. 两条历史证据勘误

完整执行链首次暴露 `AML-AE-006`、`AML-AE-014` 的参考输出会被当前生产法律依据校验拒绝。
旧 fixture 只提供一般合成摘要，缺少当前命题表要求的依据名称与明确模态；
因此“案例有法规文字”并不等于“高影响处置有可接受的依据”。

v3 仅补齐这两条 `toolFixture.legalResult` 中的合成命题映射，并在
`annotation.reviewerNote` 中记录原因。客户输入、风险、必需动作和所有标准答案保持不变。
manifest 的 `errata` 与自动测试共同限制可变字段，其他历史内容不得顺手修改。

没有放松生产校验器，也没有为获得通过率而删除冻结或报告要求。
法规名称只是复用当前项目配置的技术匹配键；合成摘要明确标识非真实法规原文。
**确定性门禁通过仍不证明真实法律适用正确，专家必须复核辖区、名单性质、主体、条件及有效法条。**

原有 RAG、助手和工作流测试集不在本轮改写范围；不能用尽调 Agent 新增数量代替它们的结果。

## 7. 如何判断数量是否够

不设“达到 100 条就够”的统一门槛。先明确验收任务、业务分层、严重错误容忍度和抽样机制。
工程回归按行为与故障覆盖判断；模型性能按独立标注与独立抽样判断。

作为样本规模说明，假设独立同分布的二项试验、预先固定失败定义、观察到零失败，
单侧 95% 失败率上限为：

```text
p_upper = 1 - 0.05^(1/n)
```

这是由零失败概率 `(1-p)^n` 得到的数学计算；
精确二项置信限的背景见 [NIST Exact Binomial](https://itl.nist.gov/div898/software/dataplot/refman2/auxillar/exacbino.htm)。

- 假想 45 个独立样本零失败，上限约 6.44%。
- 假想 90 个独立样本零失败，上限约 3.27%。
- 要在零失败条件下把该上限压到 5%，至少需要 59 个独立样本。
- 要压到 1%，至少需要 299 个独立样本。

**当前公开合成集不满足这些独立抽样、专家标注及真实模型运行前提，不能套用上限对外宣称质量。**
例如高风险漏报率必须以独立高风险样本为分母，不能用低风险案例补足数目。
存在失败、分层抽样或家族相关时需重新计算区间；若重复运行同一题，不能将重复次数当新的独立业务样本。

299 也不是监管要求或普遍上线标准，只是给定假设与目标的样本量计算。
专家应根据实际风险和业务分布决定验收阈值。

## 8. 仍未完成、不能伪造的部分

1. 两名独立领域专家标注、第三人裁决争议，核验真实法规适用并记录审核人和时间。
2. 仓库外按客户、模板与家族独立取样的正式隐藏 TEST；不能搬运当前公开样本。
3. 获准发送的数据、模型调用预算与冻结参数明确后，执行真实模型评测。
4. 真实数据库、队列、向量检索、浏览器 E2E 与负载/故障恢复验证。

这些内容不能通过生成更多合成 JSON 或把状态改成 `DOMAIN_EXPERT_APPROVED` 解决。
正式运行继续遵守 [隐藏 TEST 协议](hidden-test-protocol.md)。

## 9. 运行方式

离线验收，在 `backend` 目录执行：

```powershell
$env:RUN_LIVE_AGENT_EVAL = "false"
./mvnw.cmd "-Dtest=AgentEval*Test,ForbiddenClaimDetectorRegistryTest" test
./mvnw.cmd verify
```

前端，在 `frontend` 目录执行：

```powershell
npm.cmd test
npm.cmd run lint
npm.cmd run build
```

Live test 当前完整 DEV 为 59 条，比 v2 的 29 条进一步增加。
既定 60 分钟超时是保护上限，不承诺 59 条可在所有模型或网络条件下完成；正式运行须预估预算和时延。
单案例定位使用现有 `runDevCase` / DEV 单案例接口，不挑选最好结果冒充整集成绩。
