## 3. 确认缺陷

### R1. [P2] 正常改判冲突返回 412，页面不刷新；重新确认分支也会丢失草稿

主要位置：

- `backend/src/main/java/com/bank/aml/investigation/InvestigationService.java:215`：覆盖版本不符抛出 `IllegalStateException`。
- `backend/src/main/java/com/bank/aml/common/GlobalExceptionHandler.java:106`：上述异常映射为 HTTP 412。
- `frontend/src/views/CaseDetailView.vue:750`：形成结论仅在 409 时刷新并进入重新确认。
- `frontend/src/views/CaseDetailView.vue:833`：重新确认收到 409 后只刷新，没有保存用户新输入。

**正常业务复现：**

1. 分析员甲打开覆盖编辑，页面持有假设 revision=3、覆盖 revision=1。
2. 分析员乙对该假设改判。实际 `updateHypothesis` 将假设递增至 4，并将相关覆盖重置为 PENDING、revision 递增至 2。
3. 甲提交旧页面中的分析。`updateCoverage` 先检查覆盖 revision，抛出普通状态异常，尚未执行专用的假设版本冲突检查。
4. 接口因此返回 412。甲的页面只弹出错误，不刷新调查事实；重新打开“形成结论”时输入为空，仍可能基于旧版本提交。

**独立的页面缺口：** `reconfirmAlertCoverage` 的 409 分支虽然写着“保留输入”，实际只调用 `reloadInvestigation`。用户刚编辑的 `value` 没有保存在对话框外；再次打开时用的是数据库旧 `coverage.analysisSummary`。即使后端统一返回 409，该分支仍不能达到“刷新后保留草稿”的要求，因此两侧需一起修正。

**本轮验证：**

- 临时 Java 探针调用实际 `updateHypothesis`，观察到假设 3→4、覆盖 1→2，再调用实际 `updateCoverage` 和异常映射器，确认返回 412。仓库为 Mockito 模拟；不是数据库并发试验。
- 临时组件探针挂载实际 `CaseDetailView.vue`，点击真实模板中的按钮，模拟 API 返回 412，确认没有新增调查读取请求，第二次弹框没有原输入。
- 对重新确认入口注入接口约定的 409，确认刷新发生，但第二次弹框恢复数据库旧分析，刚编辑的草稿丢失。此项验证的是错误分支行为，不声称正常改判已经会走到该分支。

**影响：** 不会让旧结论绕过后端门禁，但会造成调查输入丢失、页面滞后和重复失败。实施说明中“409 时刷新并保留输入”的交付描述目前不成立。

**修复方向：** 对覆盖/假设的预期版本不符统一使用调查版本冲突协议；保留业务前置条件失败的原语义。形成结论与重新确认共用可保留草稿的编辑流程，冲突后显示最新判断依据及结论方向，等待用户明确确认，不自动重放。

### R2. [P2] V26 第 2 条影响查询引用了未声明的 `a` 别名

位置：`docs/ops/investigation-impact-queries-v26.sql:17`。

第 2 条“覆盖绑定的假设版本已过期”查询选择 `a.external_alert_id`，FROM/JOIN 中却只有 `alert_investigation_coverage cov` 与 `investigation_hypothesis h`，没有关联 `aml_alert a`。

该语句无法解析 `a.external_alert_id`，在 MySQL 上会产生未知列错误；迁移后的过期绑定清单不能生成。只核对列名是否在实体中存在，不能发现此类 SQL 作用域错误。

**本轮验证：** 对实际查询逐项核对 SELECT 与 FROM/JOIN，确认外层不存在别名 `a`；未在 MySQL 上执行，因此不记录数据库运行成功或实际错误码。

**修复方向：** 补充 `LEFT JOIN aml_alert a ON a.id = cov.alert_id`，与同文件其他查询一致；随后在隔离 MySQL 上执行对应阶段全部 SQL，并用已知异常数据核对结果。不要只修正这一行后再以静态核对代替脚本验收。
